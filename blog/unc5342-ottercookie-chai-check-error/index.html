    UNC5342 Delivers OtterCookie via Trojanised chai-check-error NPM Package¶

    On 12 June 2026, I identified a newly published NPM package named chai-check-error, less than twelve hours after its upload to the registry. The package is a trojanised clone of the legitimate chaijs/check-error utility library, preserving full API compatibility whilst embedding a concealed four-stage loader.

    • Stage 0 (index.js) uses a custom key derivation routine applied to a hardcoded byte array to produce AES-256-CBC key material, decrypting a URL pointing to a JSON dead-drop on jsonkeeper[.]com.
    • Stage 1, retrieved from that URL, is an obfuscated spawner that launches a detached child process with its argv0 set to [kworker/0:0] to impersonate a Linux kernel worker thread.
    • That child process fetches Stage 2 from a GitHub Gist and evaluates it directly.
    • Stage 2 is a full-featured infostealer and remote-access tool assessed as a modified OtterCookie variant, connecting to a hardcoded C2 at 178.253.38[.]166:2999 over Socket.io.

    Pivoting on the GitHub account (brendanreilly1995) identified from the Stage 2 Gist URL revealed a concurrent Contagious Interview lure campaign. The account hosts a coding-assignment repository (aigtech-assignment) presenting a Web3 backend-engineer technical test for a fictitious company, AiGTech (aigtech[.]dev). On the following day, the threat actor removed the aigtech-assignment repository from GitHub and added a new one called backend-test, which was directly linked to the weaponised chai-check-error NPM package. This link revealed the story behind the threat actor's intention. Let's dive in into the world of UNC5342.

    Attribution to UNC5342 is assessed with high confidence on the basis of the Contagious Interview delivery tradecraft, the [kworker/0:0] process-masquerading technique documented across prior OtterCookie campaigns, the OtterCookie payload characteristics consistent with malware tracked in internal research since October 2025, and the fake-employer infrastructure pattern characteristic of the cluster's recruitment-lure operations.

    Background¶

    UNC5342 is a DPRK-nexus threat cluster that has conducted financially motivated operations targeting software developers since at least 2023 through fraudulent technical-interview and recruitment schemes, widely tracked as Contagious Interview. The cluster operates under several overlapping vendor designations such as Famous Chollima, DeceptiveDevelopment, Void Dokkaebi, and distributes malware through trojanised packages across npm, PyPI, Go, crates.io, and Packagist, as well as GitHub repositories and coding-task assignments presented as part of a fabricated hiring process. From what is observed so far, targeting concentrates on developers in the cryptocurrency, blockchain, and financial-technology sectors, with the objective of harvesting developer secrets, source-control credentials, cloud tokens, and cryptocurrency wallet material.

    This analyst has tracked UNC5342's NPM-based delivery operations since October 2025. An initial investigation documented OtterCookie delivery via a malicious NPM package using Vercel-hosted infrastructure as a C2 resolver and first observed the [kworker/0:0] process-masquerading technique. A January 2026 investigation documented a refined chain using JsonSilo and Npoint.io as dead-drop relays. A March 2026 investigation identified a four-package campaign on jsDelivr using custom HTTP authentication headers to gate payload delivery. Concurrently, a distinct UNC5342 delivery line was documented using JavaScript loaders appended to legitimate package codebases and resolving payloads from TRON, Aptos, and BNB Smart Chain blockchain infrastructure.

    Part I — Trojanised NPM Package and Four-Stage Infection Chain¶

    The Package: chai-check-error¶

    As explained in the Summary section, the observed malicious package chai-check-error was published on 12 June 2026. Its name is a plausible variation on the legitimate chaijs/check-error library, the Chai assertion team's error-utility module last updated in January 2026, and would be easily confused with it by a developer browsing the registry or accepting a dependency without scrutiny.

    Unlike a typical typosquatting stub, the trojanised index.js exports a fully functional implementation of all five public API methods: compatibleInstance, compatibleConstructor, compatibleMessage, getMessage, and getConstructorName. The legitimate logic is preserved verbatim, including the original JSDoc commentary.

    The malicious logic is embedded within the getMessage function's initialisation path. A function _initMsgCache() is invoked unconditionally at module load time. Its actual behaviour — cryptographic key derivation, AES decryption, and remote payload execution — is documented in the next section.

    Stage 0 — Trojanised index.js¶

    The concealed loader operates through three sequential steps: pseudo-random substitution-box generation, position-dependent key derivation, and AES-256-CBC decryption to recover the Stage 1 URL.

    • Step 1 — Substitution-box generation (_sbox). A custom PRNG seeded with 0x9E3779B1 — the golden-ratio fractional constant used in hash-mixing functions such as Murmur3 — produces a substitution array of n bytes using the Numerical Recipes LCG parameters A = 1664525, C = 1013904223. Each iteration advances the state as s = (A * s + C) >>> 0 and extracts (s >>> 16) & 0xFF.

    • Step 2 — Key derivation (deriveSeed). A hardcoded 162-byte array _d is processed element-by-element using the substitution box. For each byte b at index i: XOR with the substitution value, apply a position-dependent subtraction (b ^ _t[i]) - ((i * 73 + 41) & 0xFF), then rotate left by three bits. The resulting characters are concatenated and the leading two-character 0x prefix is stripped, yielding a hexadecimal-encoded 80-byte binary buffer.

    • Step 3 — AES-256-CBC decryption. The 80-byte buffer is partitioned: bytes 0-31 form the 256-bit key, bytes 32-47 the 128-bit IV, and bytes 48-79 the 32-byte ciphertext. Node.js crypto.createDecipheriv('aes-256-cbc', key, iv) recovers the plaintext URL: hxxps://jsonkeeper[.]com/b/JOCBY.

    Stage 1 — JSON Dead-Drop¶

    _initMsgCache() issues an HTTPS GET to hxxps://jsonkeeper[.]com/b/JOCBY. The service returns a JSON object with a single key, cookie, whose value is a heavily obfuscated JavaScript string (Figure 3). The loader parses the response and passes the value to new Function('require', mod)(require), executing it in the current process context with access to require.

    jsonkeeper[.]com is a free JSON-storage and hosting service. Using it as a dead-drop relay rather than a dedicated domain means the Stage 1 URL survives even if the npm package is removed, as the URL is not attributed to the actor. It also blends with legitimate JSON-API traffic, and the hosted content can be updated or rotated without changing any indicator embedded in the package itself. This is a functional equivalent of the JsonSilo relay that I spotted at least some time ago.

    Three properties of this spawn call are analytically significant.

    • argv0: "[kworker/0:0]" — the spawned process's argv[0] is overridden to impersonate a Linux kernel worker thread. In ps aux and top output the process appears as a kernel thread, reducing the likelihood of detection by a responder performing ad-hoc process triage. This technique has been documented in OtterCookie samples tracked in my internal research since at least October 2025.

    • MMSCRIPT_CHILD: "1" — the environment variable is set in the child process, providing Stage 2 with a signal that it is running as an implant subprocess rather than interactively. This can be used to suppress interactive output or to branch behaviour.

    • detached: true, stdio: "ignore", .unref() — the child is fully detached from the parent npm process, its standard I/O is suppressed, and the parent's event loop does not wait for it. The npm process exits normally, and the implant continues running silently in the background.

    Stage 2 — GitHub Gist Payload Fetch¶

    The detached child process fetches and evaluates a 62-kilobyte obfuscated JavaScript file from: hxxps://gist.githubusercontent[.]com/brendanreilly1995/56ccd368682054d39a522bd443e816f3/raw

    The raw content employs the ObfuscatorIO self-executing wrapper (function(a, b){...})(encodedStringTable, checksum) with a large RC4-based string table, the same obfuscation family as the Stage 1 script retrieved from jsonkeeper[.]com.

    Stage 2 — OtterCookie RAT Payload¶

    Deobfuscation resolves the Gist content to a 752-line Node.js infostealer and remote-access tool. The capabilities are consistent with the OtterCookie family as documented in prior research and several public reports, and are assessed with high confidence as a further evolution of that family. The entire deobfuscated script can be found in the Appendix. I'll flag here some of the main RAT capabilities.

    Dependency Bootstrap¶

    On execution the implant checks for axios, form-data, and socket.io-client. Any absent dependency is installed synchronously via:

    npm install <missing> --no-save --no-audit --no-fund --loglevel=error

    with stdio: 'ignore' and windowsHide: true, ensuring silent operation in a minimal Node.js environment.

    Credential and Data Theft Modules¶

    All uploads are sent to hxxp://178.253.38.166:2999/upload as multipart POST requests bearing three custom headers: x-hostname, x-username, and x-u: "*" (a hardcoded campaign marker).

    • Browser data — Chrome, Edge, and Brave profiles are enumerated on all three platforms; the implant uploads Extension Settings directories (covering all browser-extension LevelDB stores, including cryptocurrency wallet extensions), Cookies databases, Network/Cookies, Local Storage, and Session Storage. Firefox profile directories are uploaded in their entirety.

    • Cryptocurrency wallets — Application-support directories for 1Password, Exodus, Atomic Wallet, Electrum, WinAuth (Windows), KeePassXC, Dashlane, and Bitwarden are targeted with platform-specific paths across Windows, macOS, and Linux.

    • Telegram — The tdata session directory is located and uploaded across all platforms, including the macOS sandboxed container path.

    • Developer credentials — The following artefacts are targeted explicitly:

    Part II — Pivot: AiGTech Contagious Interview Lure¶

    Discovery: The GitHub Account brendanreilly1995¶

    The GitHub URL embedded in Stage 1.1 — gist.githubusercontent.com/brendanreilly1995/... — provided an account identifier that could be pivoted further. Examining the full public profile of the account brendanreilly1995 on GitHub revealed the account to be effectively purpose-built: two public artefacts are associated with it — the Stage 2 Gist documented above, and a repository named aigtech-assignment.

    The account age, approximately two days at the time of analysis, is consistent with the cluster's documented practice of registering purpose-built lure accounts shortly before a targeted distribution campaign rather than maintaining persistent identities.

    The AiGTech Fake Company¶

    The aigtech-assignment repository links to aigtech[.]dev as the purported employer. The website presents a professionally designed Web3 technology company with a coherent brand identity, product descriptions, and a team page. The name itself impersonates several legitimate companies with similar names, which is typical for the DPRK operatives and their impersonation modus operandi.

    Pivoting from the aigtech[.]dev domain surfaced a catalogue of additional job listings visible across the website, covering multiple engineering and technical roles beyond the Web3 backend position in the lure repository. The breadth of open listings is consistent with the cluster's documented practice of constructing a complete fake-company presence to provide social-proof depth that reduces scepticism from targeted developers evaluating whether the opportunity is legitimate.

    The Coding Assignment: aigtech-assignment Repository¶

    The brendanreilly1995/aigtech-assignment repository presents a Web3 backend-engineer coding test. Looking at the README file, we can see it is professionally written and technically plausible. It describes a TypeScript service handling ERC-20 token balances, address validation, portfolio aggregation, and an Express REST API, with five intentional bugs for the candidate to diagnose and fix, a 60-90 minute time budget, and a submission workflow directed to hiring@aigtech[.]dev.

    A candidate receiving this assignment as part of a recruitment process would have no immediately visible reason to suspect it is malicious. The project files themselves are benign; the malicious code is never shipped in the archive. Instead, a single typosquatted dependency (chai-check-error@2.1.6) is declared in package.json, and the payload is only retrieved from the npm registry when the candidate runs npm install to begin the test.

    check-error-util: The Install-Time Trigger¶

    Examination of the repository's package.json reveals the mechanism by which the trojanised chai-check-error package is delivered to the candidate:

    {
  "name": "web3-coding-test",
  "dependencies": {
    "ethers": "^6.13.4",
    "express": "^4.21.2"
  },
  "devDependencies": {
    "check-error-util": "^2.1.10",
    ...
  }
}

    The package check-error-util (version ^2.1.10) serves as a thin install-time trigger. Its sole function is to ensure that chai-check-error (the package carrying the actual cryptographic loader) is loaded during npm install so that _initMsgCache() is called, and the four-stage chain fires, at the moment of project setup. This occurs before the candidate runs npm test, before they open any source file, and before they execute any project code. The separation of the trigger wrapper from the loader package is a structural choice that adds a degree of indirection. The registry entry the candidate is most likely to scrutinise (check-error-util) is itself clean or lightly obfuscated, whilst the payload resides in chai-check-error.

    A candidate targeted through a social-engineering recruitment contact and directed to this repository would traverse the entire chain in the time it takes to run two commands.

    Attribution¶

    Attribution to UNC5342 (Famous Chollima / Contagious Interview) is assessed with high confidence on the following cumulative basis.

    The delivery tradecraft is directly and specifically consistent with Contagious Interview: a fabricated employer with a professionally designed website and multiple job listings, a Web3-themed technical assignment with plausible technical depth, a GitHub account created days before deployment, and an NPM devDependency that executes silently during project setup. This pattern has been the cluster's signature delivery mechanism since at least 2023 and has been tracked continuously in internal research since October 2025.

    The OtterCookie payload — Socket.io C2, system profiling, browser credential exfiltration, cryptocurrency wallet theft, developer secret harvesting, arbitrary command execution — is consistent with public and internal documentation of the family. The expanded credential-theft target list relative to the October 2025 baseline (Bitwarden, KeePassXC, GCP application-default credentials, Azure tokens, Vault token, Kubernetes service-account token) is consistent with incremental development of the implant over the intervening eight months.

    The dual-package delivery strategy and the use of a JSON-sinkhole service as a dead-drop relay are assessed as evolutionary refinements of prior techniques rather than indicators of a different actor, given the continuity of process-masquerading and payload characteristics.

    Additional Findings¶

    During the analysis of this campaign, the threat actor removed the aigtech-assignment repository and replaced it with a new one (hxxps://github.com/brendanreilly1995/backend-test), which reuses the same technique: a package.json declaring the weaponised chai-check-error package hosted on NPM. The new assignment references a further fake company (pancaketech[.]dev, hiring@pancaketech[.]dev) impersonating a legitimate business, as indicated on the threat actor's GitHub profile.
