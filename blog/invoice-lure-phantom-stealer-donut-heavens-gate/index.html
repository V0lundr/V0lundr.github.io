    From Invoice Lure to In-Memory Injection: Phantom Stealer via Donut and Heaven's Gate

    From Invoice Lure to In-Memory Injection¶

    In January 2026, I identified a phishing campaign leveraging compromised supplier mailboxes and a multi-stage infection chain to deploy Phantom Stealer using obfuscated batch loaders, in-memory PowerShell decryption, Donut shellcode injection, and Heaven's Gate evasion. This post analyses the campaign's tradecraft, persistence mechanisms, and data exfiltration methods.

    Background¶

    Phantom Stealer is a commodity information-stealing malware family marketed within underground forums as a stealer-as-a-service (SaaS) offering. Proofpoint researchers have documented significant code overlap between Phantom Stealer and Stealerium — an open-source stealer project — with Phantom Stealer representing one of several derivatives built on that codebase.1 The malware targets browser-stored credentials, cryptocurrency wallets, FTP clients, email applications, and session tokens from platforms such as Discord and Telegram. HP's December 2025 Threat Insights Report identified Phantom Stealer as one of several purchasable malware kits being actively weaponised by threat actors to evade detection through regularly updated evasion modules.2

    Donut is an open-source shellcode generation framework that converts .NET assemblies, native executables, and scripts into position-independent shellcode executable entirely in memory, without touching disk.3 Its legitimate use in red team operations has made it a common fixture in commodity malware chains seeking to bypass file-based AV detection.

    Heaven's Gate is an evasion technique that exploits the Windows on Windows 64-bit (WoW64) compatibility layer to execute 64-bit code from within a 32-bit process. First documented around 2009, it has since been adopted by a range of malware families — including FormBook4 and ACRStealer5 — to bypass user-mode API hooks that endpoint security products place on the 32-bit Windows API layer.

    Key Highlights¶

    • Threat actors leveraged previously compromised supplier email accounts to distribute phishing messages, increasing credibility and bypassing trust-based controls
    • The campaign employed an obfuscated Batch loader, embedded Base64 PowerShell payload, AES decryption, and in-memory shellcode injection into explorer.exe to avoid disk-based detection
    • Phantom Stealer implemented WoW64 architectural mode switching to execute 64-bit code from a 32-bit process, bypassing user-mode API hooks and complicating endpoint monitoring
    • Stolen credentials, wallet data, and session artefacts were compressed, transmitted via Telegram or Discord infrastructure, and followed by local artefact cleanup to reduce forensic visibility

    Campaign Analysis¶

    In January 2026, I observed a phishing campaign targeting companies across multiple industry sectors. The campaign uses deceptive procurement-themed lures to trick employees into interacting with malicious attachments, delivering Phantom Stealer through a multi-stage attachment chain.

    Notably, attackers abused seemingly legitimate supplier accounts as sending infrastructure — sender mailboxes were likely compromised prior to the phishing activity. The campaign uniquely leveraged compromised accounts originating from the United Arab Emirates and Qatar. In some cases, the same company was targeted with several different lures, all designed to deliver the same Phantom Stealer payload.

    This campaign is not isolated. In December 2025, security researchers documented Operation MoneyMount-ISO — a campaign targeting financial services, accounting, procurement, legal, and HR functions — which used fake payment confirmation emails with malicious ISO attachments to deploy Phantom Stealer, exfiltrating data via Telegram bots and Discord webhooks.6

    Recipient domain analysis indicates targeting across industrial manufacturing, engineering, agricultural export, chemicals, and energy-related sectors in Europe and Asia.

    First Stage: Batch Dropper¶

    The attached compressed file contains a Windows Batch script executed once the archive is opened and the file is launched. The script is heavily padded with randomised variable assignments and meaningless arithmetic operations intended to obscure the script's true behaviour and delay manual analysis.

    Upon execution, the Batch file relaunches itself in a minimised window to reduce user visibility and copies its own contents into a newly created directory under the user's roaming AppData path. It then establishes persistence by adding a registry value under the current user's Run key, ensuring the malicious Batch file executes automatically at each login.

    After establishing persistence, the script prepares a secondary payload embedded directly within the Batch file itself — no external retrieval required. The embedded payload is located on the final line of the Batch file, prefixed with the distinctive marker string ::M0SjGsVxEzjdf formatted as a Batch comment, making it invisible during normal script execution.

    The script reads its own contents using PowerShell, searches for the marker to identify the start of the encoded data, extracts everything following it, and treats it as Base64 encoded content. This data is decoded and written to %TEMP%\continue.ps1 — referenced in the script via the variable UNIVERSE.

    The file is then executed immediately using PowerShell with a hidden window and execution policy bypass. Following execution of the decoded PowerShell payload, the temporary script file is deleted to minimise residual artefacts on disk.

    Second Stage: PowerShell Payload and In-Memory Injection¶

    The PowerShell code is the second-stage loader responsible for decrypting, injecting, and executing the primary malicious component entirely in memory. It transitions execution from script-based logic into native code by preparing an encrypted payload for runtime decryption and remote execution within a legitimate Windows process.

    The script begins by collecting basic host context through environment variables and enforcing single-instance execution via a named mutex using System.Threading.Mutex. An attempt is made to open an existing mutex named CRACKHONOR_Mtx — if it already exists, execution terminates immediately, preventing multiple concurrent instances. The script then verifies the presence of a running explorer.exe process and retrieves the associated PID, exiting if a valid target cannot be identified.

    The embedded payload is stored as a large Base64 blob, decoded and decrypted at runtime using the .NET cryptography framework. Decryption uses AES in CBC mode with PKCS7 padding. The encryption key is derived by computing the SHA-256 hash of a hardcoded passphrase, while the initialisation vector is statically defined and decoded from a Base64 string. Once decrypted, the resulting byte array represents raw executable code for in-memory execution.

    To execute this payload, the script dynamically compiles inline C# using Add-Type to expose native Windows API functions from kernel32.dll.

    The injection sequence uses OpenProcess to obtain a handle to explorer.exe, VirtualAllocEx to allocate remote memory, WriteProcessMemory to copy the decrypted payload, VirtualProtectEx to mark memory as executable, and CreateRemoteThread to transfer execution. The payload executes entirely within explorer.exe's address space without ever being written to disk as a standalone executable.

    After successful injection, the script enters a persistent monitoring loop — if explorer.exe terminates or restarts, the script repeats the injection routine against the new instance, ensuring continued execution across process restarts.

    Third Stage: Donut Shellcode Loader¶

    The decrypted payload injected into explorer.exe is position-independent shellcode generated using Donut version 0.9.2.3 This shellcode serves as the third stage and is responsible for unpacking and executing the final payload — a .NET assembly identified as Phantom Stealer.

    The AES key was derived from the SHA-256 hash of the passphrase restore_31_phazzy Lee, with the initialisation vector decoded from the embedded Base64 value S+hKtckT2gd+1tyosBp/LA==.

    The shellcode structure follows the documented Donut framework architecture. Execution begins with a relative CALL instruction at offset zero that jumps over approximately 600 kilobytes of encrypted payload data to reach the unpacker stub at offset 0x9329D.

    API resolution is performed entirely without import table entries through PEB traversal, matching the implementation in Donut's /peb.c source file. The function at offset 0x9612D accesses the Thread Environment Block via the GS segment register, walks to the PEB loader data structures, and enumerates loaded modules to locate required DLLs.

    For each dependency, the loader parses the PE export directory and computes a hash of exported function names for comparison against precomputed values embedded in the shellcode configuration.

    Phantom Stealer Analysis¶

    Beyond standard obfuscation, the analysed sample incorporates advanced runtime evasion that distinguishes it from typical commodity stealers. Static analysis of the extracted .NET assembly reveals a class named HeavensGate within the Stub namespace, indicating the malware implements architectural mode switching to circumvent endpoint security monitoring.

    Heaven's Gate: Architectural Mode Switching¶

    The Heaven's Gate technique exploits the WoW64 compatibility layer to execute 64-bit code from within a 32-bit process. The fundamental principle relies on the fact that 32-bit processes running under WoW64 are hosted within a native 64-bit process, with the 64-bit ntdll.dll loaded at initialisation. Security products that instrument only the 32-bit ntdll.dll remain blind to system calls issued directly through the 64-bit layer.

    The HeavensGate class first verifies execution within a 32-bit process context, then resolves critical functions from the 64-bit ntdll.dll — including LdrLoadDll, LdrUnloadDll, LdrGetDllHandle, and LdrGetProcedureAddress — through custom PEB traversal routines implemented in the Utils64 helper class. A static boolean field named operational gates all subsequent 64-bit execution attempts.

    The core implementation resides in the Execute64 method and its associated shellcode stub stored in the Wow64ExecuteShellCode byte array.

    This shellcode performs the critical code segment register manipulation — switching from the 32-bit segment selector 0x23 to the 64-bit selector 0x33 through a far jump instruction, then transitioning back to 32-bit mode after execution completes. This allows Phantom Stealer to call 64-bit versions of LoadLibrary and GetProcAddress, loading and invoking functions from 64-bit DLLs while evading any monitoring hooks present in the 32-bit execution layer.

    Data Exfiltration via Telegram Bot API¶

    Phantom Stealer uses the Telegram Bot API as its primary exfiltration channel — a technique increasingly favoured by commodity stealers due to its reliability, encryption in transit, and the difficulty defenders face in blocking legitimate Telegram infrastructure without disrupting business operations.

    The TelegramSendLogs class implements the complete exfiltration workflow. The SendReportAsync method orchestrates upload of harvested data files through the UploadToTelegram helper class before transmitting a formatted summary message.

    After upload, the malware attempts to delete local evidence — removing .txt, .png, and .json files from its working directory as a basic anti-forensics measure. The Telegram bot token and chat identifier are stored in the Config class and retrieved through StringsCrypt.DecryptConfig, which decrypts ENCRYPTED:BncRbgTGet4L+mKqD8dz7h8EdEcrI2Pbm5InYO5Ff/I= at runtime to reveal the base API endpoint.

    The SendMessageInfoAsync method constructs a detailed victim profile in Telegram's Markdown parsing mode, including Windows version, username, computer name, detected antivirus product, gateway IP, internal IP, and external IP. The report provides a statistical breakdown of harvested data by type — passwords, credit cards, cookies, browser wallet extensions, desktop cryptocurrency wallets, FTP credentials, VPN accounts, and session data from Outlook, FoxMail, Telegram, Discord, and WinScp.

    Configuration flags indicating whether persistence, keylogging, screenshot capture, clipboard hijacking, and file grabbing modules are active are appended, giving the operator full visibility of implant capabilities. Notably, the message footer contains direct attribution to the malware author via the Telegram handle Oldphantomoftheopera and the marketing website phantomsoftwares[.]site, confirming the stealer-as-a-service distribution model.
