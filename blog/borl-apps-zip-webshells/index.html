    APPS.zip: A Compromised BORL Web Application and Two Webshells¶

    Executive Summary¶

    On 7 July 2026 a 60 MB ZIP archive was submitted to VirusTotal from a single unique source from India. The archive with a filename APPS.zip, contains what appears to be the on-disk web root of an ASP.NET application belonging to Bharat Oman Refineries Limited (BORL). BORL operates the Bina refinery in Madhya Pradesh and is a wholly-owned subsidiary of Bharat Petroleum Corporation Limited (BPCL), the Government-of-India-owned oil major into which it was amalgamated in 2022; ownership ultimately sits under the Ministry of Petroleum and Natural Gas. The application itself dates from roughly 2017-2024 and looks legitimate. However, three ASP.NET files added between 30 June and 3 July 2026, days before the archive was uploaded, are webshells - which opens up a lot of questions.

    As of the time of writing, I have found no public reporting of this intrusion, and neither BORL nor BPCL has publicly disclosed or confirmed a breach consistent with this activity. Everything below is derived solely from the archive submitted to VirusTotal.

    After the analysis, the two distinct webshell families are:

    1. A full-featured manual-operator ASPX shell (borlapi.aspx) offering file browser, file editor, file uploader, cmd execution, and an SQL query manager, protected by the hard-coded password Admin1234@_.
    2. A socket-relay / tunnelling webshell (borel.aspx) whose protocol vocabulary (CONNECT, FORWARD, READ, DISCONNECT), 40-slot object[] info array, and per-request base64-plus-substitution encoding are structurally identical to the ASPX template shipped by Neo-reGeorg, a fork of SensePost's reGeorg maintained by a Chinese researcher (GitHub L-codes) and repeatedly attributed by commercial intelligence to China-nexus intrusion sets.

    Background¶

    The two tunnelling shells in this archive belong to a well-known lineage. SensePost released reGeorg, the successor to their earlier reDuh tool, which turns a webshell on a bastion host into a SOCKS proxy so an operator can pivot into a network from a single foothold.1 A researcher publishing under the GitHub handle L-codes later released Neo-reGeorg, an aggressive refactor of reGeorg designed to be harder to fingerprint: it disguises its traffic as ordinary base64, wraps its data in a byte-length-value format, and can hide its idle response inside a decoy page such as a fake 404.2 Neo-reGeorg is open-source and used by red teams worldwide, but it has also become a common post-exploitation tunnel in intrusions attributed to several China-nexus intrusion sets, which is what makes its appearance here relevant to the attribution question later in this post.

    The manual borlapi.aspx shell comes from a different and older tradition: the WSO / c99 family of administrative webshells that bundle a file browser, editor, uploader, command runner and database client behind a single password prompt. That lineage is commodity tooling, mirrored across dozens of public repositories, and carries little attribution weight on its own.

    The overwhelming majority of files in the archive carry mtimes between 2017 and 2024, which is plausible for a long-lived enterprise application.     The three-day cadence of the drops (30 June -> 2 July -> 3 July) is suggestive of an operator iterating: dropping a manual shell first, then adding tunnelling capability, then dropping a second copy of the tunnelling shell into a less-attention-getting subdirectory (Content/, which normally holds CSS and images).

    borlapi.aspx - Manual-Operator WSO-Style Shell¶

    borlapi.aspx is a straightforward, unobfuscated ASP.NET Web-Forms page. Its Page_Load handler dispatches on a base64-encoded act query-string parameter to one of six operator features:

    The command tokens are only cosmetically hidden (base64 with the literal ASCII strings visible after one decode). The shell's cookie name for its working-directory state is shell_path. Password check is a plaintext comparison against the hard-coded Admin1234@_.

    Feature-wise this is a WSO (Web Shell by oRb) / c99-lineage administrative shell ported to ASP.NET - file browser + editor + uploader + shell command + SQL client + logout.3 The "dark" style constant and the modal layout in the HTML confirm the WSO visual heritage. Nothing in the code identifies a specific author or operator. In other words, the password is generic, no unique tag or version string, and no C2 callback. It is best treated as commodity tradecraft, the sort of thing an operator can grab from any of dozens of GitHub mirrors.

    Kaspersky's Backdoor.ASP.Agent.co verdict on the parent ZIP is consistent with this file being the primary trigger, but the more interesting artefact, from an attribution perspective, is borel.aspx.

    borlapi.aspx Targets SQL Server Specifically¶

    Beyond the action tokens covered above, extracting the full set of base64 tokens embedded in the shell reveals hardcoded discovery queries:

    • SELECT * FROM INFORMATION_SCHEMA.TABLES;
    • SELECT name FROM master.dbo.sysdatabases

    master.dbo.sysdatabases is a Microsoft SQL Server catalogue view. It does not exist on MySQL, PostgreSQL, or Oracle. As far as I could understand, it is present on SQL Server 2000 and later. The shell also emits IIS-specific server-variable lookups (LOCAL_ADDR, SERVER_SOFTWARE) rather than generic HTTP headers.

    Combined with the fact that the compromised application runs on Microsoft SQL Server, this is consistent with an operator who either knew the target stack in advance or was using a shell whose defaults happened to fit. It is a weak signal on its own, but it mildly favours a not-fully-blind attacker over a scanner dropping whatever landed first.

    The shell also supports finer-grained file operations than the top-level tokens suggest. Extracted sub-tokens include fedit_read, fedit_write, fedit_mkdir, fedit_remove, and fedit_rename, plus cookie state keys shell_pass and shell_sql, and the MIME type application/force-download for file exfiltration. In other words, borlapi.aspx is a full file-and-database administration console, not just a command runner.

    borel.aspx - A Tunnelling Shell Structurally Consistent with Neo-reGeorg¶

    borel.aspx at BORLAPI/borel.aspx is 19,937 bytes and aggressively obfuscated. The obfuscation is a stack of three techniques.

    1. C-style Unicode escape sequences in identifiers. Every identifier is written as a mix of ASCII characters and \uXXXX / \UXXXXXXXX escapes. In C# source these render as literal ASCII text of six or ten characters each. The C# compiler resolves them at compile time and treats the resulting identifiers as equivalent to their ASCII form. So StrTr, \u0053trTr, and Str\u202aTr all compile to the same symbol. A human reader sees noise. The compiler sees one identifier.
    2. Random noise comments. Every second line carries a 30-character base62 comment like /*aMbi0gltl4OXlm6UJ0x5zHRIkjImRF*/. These comments have no semantic content. They exist only to defeat naive string signatures.
    3. Dot-separator obfuscation on select string literals. The error strings returned by the CONNECT verb are written with periods between every character. Instead of "Port close" and "Port filtered", the file contains "P.o.r.t c.l.o.s.e" and "P.o.r.t f.i.l.t.e.r.e.d". This defeats simple grep "Port close" style detections. The strings still convey the same information to the operator, who reads them by eye rather than by regex.

    Normalising the file, resolving the escape sequences and stripping the noise comments, reveals a source that matches the ASP.NET template shipped by Neo-reGeorg (github.com/L-codes/Neo-reGeorg), a widely-used fork of SensePost's original reGeorg. Neo-reGeorg is maintained in a bilingual (Chinese/English) repository by an author who publishes primarily in Simplified Chinese and whose tooling has been observed in intrusions attributed to multiple China-nexus intrusion sets.

    // Substitution codec. Wire encoding is base64(payload) then StrTr(en -> de).
// The reader inverts with StrTr(de -> en) then base64-decode.
public String StrTr(string input, string frm, string to) {
    String r = "";
    for (int i = 0; i < input.Length; i++) {
        int index = frm.IndexOf(input[i]);
        r += (index != -1) ? to[index] : input[i];
    }
    return r;
}

// Unpack a 40-slot object[] from a byte stream. Wire layout is a stream
// of triples: (byte tag)(int32 BE length + K)(payload of length bytes),
// where K = 68903463 is a fixed additive obfuscator both sides know.
// Slots 2..9 are strings (see command constants below). Anything else
// stays as a byte[].
public static Object[] blv_decode(byte[] data) {
    Object[] info = new Object[40];
    int i = 0, data_len = data.Length, b;
    byte[] length = new byte[4];
    MemoryStream dataInput = new MemoryStream(data);
    while (i < data_len) {
        b = dataInput.ReadByte();                       // tag
        dataInput.Read(length, 0, length.Length);       // length prefix
        int l = bytesToInt(length) - 68903463;          // subtract additive K
        byte[] v = new byte[l];
        dataInput.Read(v, 0, v.Length);
        i += (5 + l);
        info[b] = (b > 1 && b <= 9) ? (object) Encoding.Default.GetString(v)
                                    : (object) v;
    }
    return info;
}

// Pack a 40-slot object[] back into the byte-triple stream.
// Slots 0 and 39 are stuffed with fresh random padding on every response
// (5..20 bytes each) to break naive size fingerprinting.
public static byte[] blv_encode(Object[] info) {
    Random r = new Random();
    info[0]  = randBytes(r, 5, 20);
    info[39] = randBytes(r, 5, 20);
    MemoryStream buf = new MemoryStream();
    for (int b = 0; b < info.Length; b++) {
        if (info[b] == null) continue;
        byte[] v = (info[b] is String) ? Encoding.Default.GetBytes((String) info[b])
                                       : (byte[]) info[b];
        buf.WriteByte((byte) b);
        byte[] l = intToBytes(v.Length + 68903463);     // add additive K
        buf.Write(l, 0, l.Length);
        buf.Write(v, 0, v.Length);
    }
    return buf.ToArray();
}

// randBytes / intToBytes / bytesToInt: uninteresting helpers.
// bytesToInt is big-endian. intToBytes is its inverse.

// Wire-protocol slot constants for the info[] array:
int DATA          = 1;   // payload bytes for FORWARD / READ
int CMD           = 2;   // "CONNECT" | "DISCONNECT" | "FORWARD" | "READ"
int MARK          = 3;   // operator-supplied session key (dictionary index)
int STATUS        = 4;   // "OK" | "FAIL"
int ERROR         = 5;   // error text on FAIL
int IP            = 6;   // target host for CONNECT (name or IP)
int PORT          = 7;   // target port for CONNECT
int REDIRECTURL   = 8;   // optional. re-issue whole request to another URL
int FORCEREDIRECT = 9;

// Idle-response banner. See the Idle-Page Banner subsection below.
String GeorgHello =
    "lyhRqWcEQZ3WvWREPi2aWQpnM0YYxnX8GjceQFXl3gKDAijmvFpqDbXEsLpfALkaMh2fsZmcM1YM70hgWiVaTy1Rl/==";

// The two runtime substitution alphabets. 'en' is the standard base64
// alphabet. 'de' is a permutation of it. StrTr swaps between them.
String en = "ABCDEFGHIJKLMNOPQRSTUVWXYZabcdefghijklmnopqrstuvwxyz0123456789+/";
String de = "kcyZh0ntTpDqM3ElAPWFzjQLvmx7IsG4/X+w6VC89Yor2RuSfegb1Uia5dBNOKHJ";

// Entry point:  Read POST body, substitution-decode, unpack info[],
//               dispatch on info[CMD], pack response, substitution-encode, Write.
    info[CMD] Preconditions What the shell does Response
    CONNECT info[IP], info[PORT] set Open a TCP Socket to IP:PORT. Store it in Application[MARK]. Set the socket non-blocking with a 2-second connect timeout. STATUS="OK", or STATUS="FAIL" with ERROR set to "Port close" or "Port filtered"

    READ Application[MARK] exists Loop s.Receive() into a MemoryStream up to 512 KiB or until short read. Return via info[DATA]. STATUS="OK", info[DATA] = <bytes>
    DISCONNECT Application[MARK] exists s.Close(). Application.Remove(MARK). (silent, no encoded response body)

    The Idle-Page Banner: A Neo-reGeorg Fingerprint¶

    The most attribution-relevant string in the file is the GeorgHello constant. It is what an unauthenticated outside probe sees when it GETs /borel.aspx with no body. The shell writes StrTr(GeorgHello, de -> en) and base64-decodes it before returning the result to the caller. Running that inverse reveals the plaintext.

    Obfuscated banner constant:
    lyhRqWcEQZ3WvWREPi2aWQpnM0YYxnX8GjceQFXl3gKDAijmvFpqDbXEsLpfALkaMh2fsZmcM1YM70hgWiVaTy1Rl/==

After StrTr(de -> en):
    PCEtLSBOWDNSYStOR2s3SWJGMFppaGhneVBxWThPNy9KQ2VZYTJLKzhOdXJwQXA3MEswdDZBM0pMbFEyS2l3IC0tPg==

After base64-decode:
    <!-- NX3Ra+NGk7IbF0ZihhgyPqY8O7/JCeYa2K+8NurpAp70K0t6A3JLlQ2Kiw -->

    The HTML-comment-wrapped random token is the canonical Neo-reGeorg idle-page response. The original SensePost reGeorg used a plaintext greeting of the form Georg says, 'All seems fine'. The L-codes fork changed it to an HTML-comment token so the response can be embedded inside a decoy HTML wrapper page without breaking rendering. The token between <!-- and --> is what the Neo-reGeorg client extracts and uses as the per-deployment session key that seeds StrTr.

    Content/borel.aspx - The Same Shell, but Renamed¶

    The second copy of the tunnelling shell, dropped one day later into BORLAPI/Content/, is only 8,390 bytes and carries none of the Unicode obfuscation. Every identifier has been mechanically renamed to placeholders of the form X<n>, spanning at least X1 through X71. The renaming is not a simple sequence. X8 is blv_decode, X19 is blv_encode, X22 is randBytes, X17 is bytesToInt, X1 is StrTr, and the command verb variable is X71. The gaps suggest a name-scrambling pass rather than a linear rename.

    Structurally the two files are the same webshell. After normalisation, every structural marker matches: same six functions with the same signatures and roles, same four verb dispatch (CONNECT, DISCONNECT, FORWARD, READ), same 40-slot object[] info layout with slots 0 and 39 reserved for random padding, same slot semantics for indices 1 through 9, same optional HTTP-proxy branch on REDIRECTURL, same Application[MARK]-persisted socket, same 2-second BeginConnect timeout, and same 512 KiB READ cap. Renaming the X<n> placeholders back to their file 2 equivalents and diffing structural tokens against file 2 yields an empty diff. No code path exists in one file that is absent from the other.

    The two files are not byte-copies of each other. They differ in three specific ways, all of which are per-build values that Neo-reGeorg's generator randomises on each run:

    • The additive constant K is 68903463 in file 2 and 1699217646 in file 3.
    • The de substitution alphabet is a different 64-character permutation in each file.
    • The GeorgHello banner decodes to a different <!-- <random> --> token in each file (<!-- NX3Ra+NGk7Ib... --> versus <!-- w75n/40s0sJS... -->).

    It is highly likely both came from the same operator toolkit or the public Neo-reGeorg repo. The simplest interpretation is that the operator ran neoreg.py generate twice, producing two independent builds, then applied a different post-processing pipeline to each. File 2 was obfuscated with three techniques (Unicode escapes in identifiers, random noise comments, and dot-separator obfuscation on error strings). File 3 was mechanically renamed to X<n> placeholders and left otherwise clean. Neither file is a fallback derived from the other. They are two separate Neo-reGeorg endpoints planted on the same host across two consecutive days.

    Attribution - What the Tooling Suggests, and What It Does Not¶

    We now turn to the harder question: who dropped these files? The honest answer is that this artefact alone does not settle it. What follows is a hypothesis with its evidence and its caveats.

    The China hypothesis¶

    Working hypothesis (low confidence): the intrusion sits inside the broad envelope of China-nexus targeting of Indian critical infrastructure, most plausibly by an intrusion set that habitually uses Neo-reGeorg as a post-exploitation tunnel.

    The supporting evidence is twofold:

    • Tooling - borel.aspx and Content/borel.aspx reproduce, function-for-function, the ASP.NET template of L-codes/Neo-reGeorg, whose author publishes in Simplified Chinese. Neo-reGeorg is by no means China-exclusive, and it is open-source, mirrored widely, and used by red teams globally, but it is the standard tunnelling implant used in China-nexus intrusions across various security vendor datasets.
    • Target - BORL is a wholly-owned subsidiary of BPCL, a Government-of-India-owned refiner. Indian downstream oil-and-gas is a documented targeting priority for multiple China-nexus intrusion sets, coinciding with Chinese-state strategic interest in South Asian energy logistics and Indian Ocean supply chains. The shell's hardcoded SQL Server catalogue queries (see the borlapi.aspx targets SQL Server subsection) suggest the operator either knew or had scanned enough to know that the target stack was IIS plus MSSQL. This is a soft signal and should not be leaned on for attribution, but it mildly disfavours the fully opportunistic reading in which the operator drops a shell and only afterwards discovers what the box is running.

    What is Missing to Raise Confidence¶

    The following items are absent from this sample:

    • No Chinese-language artefacts:
      • Zero CJK code points in any of the three ASPX files, no gb2312/gbk charset references, no Chinese-language comments.
    • No unique operator infrastructure:
      • No hard-coded C2 domain or IP, no key material tying to a known cluster, no user-agent string, no cookie name that resembles previously-published Neo-reGeorg configuration in the wild.
    • No hash overlap:
      • Neither the archive nor any of the three shells matches a known tracked indicator. In addition, VT lists no similar samples beyond another submission of the same file.
    • No knowledge of initial access:
      • We can see the shells but not the initial access. The archive does not include IIS logs, w3wp.exe process traces, or a captured exploit request.

    Alternative Hypotheses that Must be Kept Alive¶

    Two other reasonable readings of the evidence deserve to remain on the board:

    • Opportunistic eCrime
      • The manual borlapi.aspx shell is generic WSO-lineage tooling routinely dropped by broad-scope scanning crews.
    • Iran-nexus opportunism
      • ASPX-shell activity against Indian entities has also been linked to Iran-nexus intrusion sets that pair IIS webshells with privilege-escalation tooling such as JuicyPotato (Fox Kitten). Nothing in the sample rules this reading out.

    The archive as it stands is insufficient to distinguish these hypotheses. The tooling leans China-nexus and the sparse tradecraft is compatible with any of the three.

    Confidence statement¶

    Working theory, held with low confidence: a China-nexus operator found an internet-facing BORL or BPCL host, exploited it, and dropped Neo-reGeorg on top to relay traffic back through the compromised server. This is the reading that requires the fewest assumptions. It is not the only reading that fits the evidence, and the artefact alone cannot rule out an eCrime crew or an Iran-linked one using the same open-source tooling.
