    UNC5342 Blockchain Dead-Drop Loader¶

    Summary¶

    While tracking DPRK-nexus weaponised package activity, I pivoted from a Socket Threat Research report published on 31 May 2026 describing a UNC5342 (Famous Chollima) JavaScript loader appended to the development branch of a legitimate Packagist-listed PHP package.1 Using the loader's distinctive in-file obfuscation stub as a VirusTotal Intelligence content selector, I identified a further sample sharing the same builder, injected into the codebase of an AI SaaS platform for padel in Spain.

    The loader is nearly identical across the observed samples: a JavaScript stage appended to an otherwise-legitimate file behind a large whitespace gap, executing within the Node.js runtime and resolving its second-stage payload from cryptocurrency blockchain infrastructure (TRON, Aptos, and BNB Smart Chain RPC services) used as a dead-drop resolver rather than a conventional command-and-control domain. Only a per-build campaign marker and the host file vary between samples (the obfuscation framework, decoder seed, and resolver design are constant).

    It is highly likely that the affected application is a legitimately-built commercial product compromised through injection rather than an actor-authored artefact, and as a realistic possibility that the compromised codebase is itself being repurposed as Contagious Interview lure material for subsequent developer victims. Family attribution to the UNC5342 cluster is assessed with high confidence on the basis of a shared loader builder and delivery tradecraft consistent with Socket's reporting.

    Background¶

    UNC5342 is a DPRK-nexus threat cluster that has targeted software developers since at least 2023 through fraudulent technical-interview and recruitment schemes, an activity set widely tracked as Contagious Interview. The cluster is reported under several overlapping vendor designations (including Famous Chollima, DeceptiveDevelopment, and Void Dokkaebi), and its operations are characterised by the distribution of malware through trojanised packages across multiple open-source ecosystems (npm, PyPI, Go, crates.io, and, more recently, Packagist), GitHub repositories, and coding-task assignments presented as part of a hiring process. Targeting has historically concentrated on developers in the cryptocurrency, blockchain, and financial-technology sectors, with the operational objective of harvesting developer secrets, source-control credentials, cloud and CI/CD tokens, and cryptocurrency wallet material from compromised workstations.

    On 31 May 2026, Socket Threat Research published an analysis of a UNC5342 loader injected into the development branch dev-drewroberts/feature/test-case of the legitimate Packagist-listed PHP package roberts/leads.1 Socket assessed the activity as a likely repository or branch compromise, a poisoned-branch workflow consistent with a Contagious Interview lure, rather than a package authored as malicious from the outset; the package's stable release line did not exhibit the indicators. The malicious code was appended to the tailwind.js configuration file behind a large whitespace gap and, once deobfuscated, behaved as a JavaScript loader that resolved its payload from blockchain infrastructure (TRON and Aptos transaction data as payload pointers, BNB Smart Chain RPC transaction input as encrypted payload material), decrypted it with hardcoded XOR keys, executed it via eval(), and spawned a hidden detached node -e second stage. Public reporting attributes the downstream payloads of this loader to the InvisibleFerret and BeaverTail families.23

    This note documents a pivot from that report. The in-file artefacts Socket described, principally the loader's obfuscation framework and decoder seed, provided durable, content-searchable selectors that proved to be shared across multiple samples and host files, enabling the identification of further victims beyond the originally reported PHP package.

    Pivot Methodology¶

    The pivot proceeded from content, not infrastructure. Socket's report did not publish a conventional command-and-control domain to track. The loader resolves its payload from blockchain RPC services rather than a fixed host, so the durable selectors were the loader's own in-file artefacts. Critically, Socket itself published these artefacts: its "Suggested local check" section provided a grep command intended for analysts to scan their own developer machines, listing the loader's distinctive strings, and its "Deobfuscation Findings" and "Indicators of Compromise" sections documented the same values.1 Among the strings Socket published were the obfuscated decoder variable _$_1e42, the decoder seed rmcej%otb%, and the campaign marker global['!'] (observed as 9-0264-2, expanding to A9-0264-2).

    The initial selector for finding additional samples was the decoder stub variable _$_1e42, an unusual token unlikely to collide with legitimate code:

    content:"_$_1e42"

    This returned files beyond Socket's original roberts/leads sample. Examination confirmed the hits shared the full obfuscation construction, not merely the variable name: the same decoder function fed the seed rmcej%otb% with the multiplier 2857687, and the same global[_$_1e42[0]]=require reconstruction. The seed string was used as a corroborating second selector, being even less prone to coincidental collision:

    content:"rmcej%otb%"

    The observed sample contained an injection into an application source file of the affected application; despite arriving in a different host-file type like in the Socket research, it carried an identical decoder stub. The differences were limited to the campaign marker (9-0264-2 in Socket's case, 9-33 here) and the host file into which the loader was appended. The decoder framework, the rmcej%otb% seed, the multiplier, and the blockchain-resolver design were the same.

    Loader Family Analysis¶

    Naming and Prior Reporting¶

    The loader analysed here has been documented publicly under several names, reflecting different vendors and different scopes of the same activity. Google's Mandiant and Threat Intelligence Group, relayed by the Canadian Centre for Cyber Security, track the blockchain dead-drop technique as EtherHiding and the specific multi-stage downloader as jadesnow.42 OpenSourceMalware track the obfuscator and an associated mass GitHub-injection campaign as PolinRider, documenting the identical decoder signature (rmcej%otb%, multiplier 2857687, variable _$_1e42) and the same blockchain wallets and XOR keys recovered in this analysis.3 Ransom-ISAC and Crystal Intelligence describe the same chain as Cross-Chain TxDataHiding.5 Public reporting attributes the downstream payload to the InvisibleFerret and BeaverTail families.23

    Obfuscation Structure¶

    The loader analysis showed that the appended stub was built from four nested decoding layers, each feeding the next:

    1. A first decoder, assigned to the variable _$_1e42, performs a seeded Fisher-Yates-style shuffle of the seed string rmcej%otb% with the multiplier 2857687, followed by a character-substitution pass. It yields a small string table; the loader immediately uses it to reconstruct global['r'] = require, masking the require reference from naive static scanners.
    2. A second decoder, sfL, of the same shuffle design but different constants, expands two large encoded blobs: the first into a third decoder, and the second into the loader body.
    3. The third decoder is a dictionary or word-substitution decompressor that expands the loader body into readable JavaScript bearing a single remaining string table, _$_ccfc.
    4. A final decoder resolves _$_ccfc into the operational strings, the API paths, method names, cryptocurrency addresses, and XOR keys, on which the loader depends.

    The salient point for hunting is that the campaign marker (global['!'], here 9-33) is the only element that meaningfully rotates between builds, alongside the host file. The decoder construction, the seed rmcej%otb%, and the multiplier are invariant across all examined samples, and are therefore the reliable family selectors. This is corroborated by OpenSourceMalware, who independently documented the same four-layer structure and the same ('rmcej%otb%', 2857687) / _$_1e42 signature across their campaign dataset.3

    Payload Resolution: a Blockchain Dead-drop¶

    Once decoded, the loader is an asynchronous function with no hardcoded command-and-control domain. Instead it resolves its payload through public cryptocurrency blockchain infrastructure used as a dead-drop, a design that places the controlling pointer and the payload body on immutable, high-availability public ledgers that are impractical to take down and that blend with legitimate blockchain traffic.

    The resolution proceeds in two stages, each independently parameterised with its own wallet, account, and decryption key:

    • The loader first queries the TRON network via api.trongrid.io, retrieving the most recent outbound transaction for a hardcoded wallet and extracting a pointer from its raw_data field (hex-decoded, reversed, and reassembled). Should this fail, it falls back to the Aptos network via fullnode.mainnet.aptoslabs.com, reading the pointer from a hardcoded account's latest transaction payload.
    • Using that pointer, the loader issues a JSON-RPC eth_getTransactionByHash request to BNB Smart Chain (bsc-dataseed.binance.org, falling back to bsc-rpc.publicnode.com) and reads the transaction's input field as the encrypted payload body. The body is then XOR-decrypted with a hardcoded repeating key.

    Execution: Two Stages and a Hidden Child Process¶

    The loader runs two payloads in sequence, each resolved through the mechanism above with a distinct wallet and key:

    • The first payload is executed in-process via eval().
    • The second is executed by spawning a detached child process: node -e <payload>, with detached: true, stdio: 'ignore', and windowsHide: true, so the second stage runs as an independent, windowless background process that survives the parent and produces no visible console. The campaign marker is propagated into the child through global['_V'], so the second stage inherits the build tag. An eval() of the same payload is retained as a fallback should the spawn fail.

    A thirty-second self-throttle (global['_p_t'], compared against Date.getTime()) prevents the loader re-running on rapid re-require, reducing duplicate execution and associated noise.

    The second-stage payloads themselves were not recovered. They do not reside in the file; they are retrieved at runtime from the blockchain, the payload pointer from a TRON transaction (Aptos as fallback) and the encrypted payload body from the referenced BNB Smart Chain transaction. Recovery therefore requires an on-chain retrieval of the relevant transactions followed by XOR decryption with the recovered keys, and is recorded as an outstanding task.

    Relationship to the Socket-reported Sample¶

    Deobfuscation of the 9-33 sample resolved the operational string table to indicators that are identical to those Socket published for the roberts/leads case: the same two TRON wallets, the same two Aptos accounts, the same two XOR keys, and the same RPC hosts.1 The samples are therefore assessed with high confidence to originate from the same builder and to share the same staging infrastructure, not merely the same technique. They are not byte-identical: the campaign marker differs (9-33 against 9-0264-2), the host file differs (the application route module AccountDataRoutes.js against tailwind.js), and the per-build encoded inner strings differ.

    The Affected Application¶

    The host of the 9-33 sample appears to be a real commercial product: a multi-tenant SaaS platform for padel and tennis club management, built for the Spanish market by a third-party software vendor and marketed as an AI-assisted assistant for clubs. It's worth noting that the identifying details are masked throughout.

    The platform looks like a substantial build, not a thin shell: a Node.js, Express, and MySQL backend that integrates with established court-management platforms (Playtomic, Syltek, Taykus) as a complementary automation layer, with booking automation, Stripe subscription billing, WhatsApp Business messaging, MQTT venue and lighting control, and an energy-management integration. It is publicly documented as an associate member of an international padel industry body since February 2025, with a public website and social-media presence.

    Injection Footprint and Deployment Path¶

    Across the entire codebase, the loader was present in exactly one file: AccountDataRoutes.js, the Express route module handling account and Stripe billing data. Every other component, the services, controllers, middleware, scheduled jobs, utilities, the application entry point app.js, and the dependency manifests, was clean. The malicious JavaScript was appended after the file's legitimate module.exports = router; behind a large whitespace gap, the same parasitic-append pattern Socket documented for the tailwind.js case. The route is mounted in app.js, so the loader executes whenever the application loads that module.
